## 1. 서비스 개요

**쏙핀은 SNS·지도 앱에서 발견한 장소 링크를 방(Room)에 모아두고, 친구들과 함께 다음 약속 장소를 고르는 서비스다.**

> "카톡방에 흘러간 링크, 그만 찾아 헤매세요. 방에 모아두면 약속 잡을 때 바로 꺼내 써요."
> "'여기 어때?'는 이제 그만. 친구가 들어오면 저장한 장소가 한눈에 모여요. 다음 약속 장소, 여기서 같이 골라요."

### 해결하는 문제

- 인스타그램 등에서 발견한 가고 싶은 장소가 카톡방·북마크에 흩어져 있어, 약속을 잡을 때 다시 찾기 어렵다.
- 장소 링크(게시물)에는 구조화된 장소 정보(이름·주소·좌표)가 없어, 지도에서 다시 검색하는 수고가 필요하다.
- 모임 단위로 장소 후보를 모으고 의견을 나눌 공간이 없다.

### 핵심 컨셉

- **공유 시트로 유입**: 인스타그램 등에서 시스템 공유 시트를 통해 링크를 쏙핀으로 보내면, 장소가 자동으로 추출되어 방에 핀으로 저장된다.
- **방(Room) 중심 구조**: 모든 핀은 방에 속한다. 온보딩 시 생성되는 개인방과, 초대 코드로 친구를 모으는 공동방이 있다.
- **카드 탐색**: 홈에서 방의 핀을 카드 덱으로 탐색하고("꾹 눌러둔 장소, 다시 꺼내볼까요?"), 지도·리스트로도 확인한다.
- **로그인 없는 MVP**: 계정 가입 없이 `device_id`로 최초 등록하고, 이후 요청은 서버 발급 토큰으로 인증한다. (→ [2.1 인증·보안 모델](#21-인증보안-모델-mvp))

## 2. 목표 / 비목표

### 목표 (MVP 범위)

- 링크 공유 → 장소 추출 → 핀 저장의 핵심 루프가 **인스타그램 링크** 기준으로 동작한다.
  - 네이버지도 / 구글맵 / 수동 입력은 MVP 확정 범위가 아니다. (→ [7. 미결 사항](#7-미결-사항-open-questions) 1번)
- 개인방·공동방을 만들고, 초대 링크(e.g, `ssokpin.app/r/{code}`)로 친구가 합류할 수 있다.
- 방의 핀을 홈 카드 덱 / 지도 뷰 / 리스트로 탐색하고, 장소 상세에서 코멘트를 나눌 수 있다.
- 핀을 다른 방으로 공유(복제)할 수 있다.

### 비목표 (MVP에서 다루지 않음)

- 소셜 로그인·계정 시스템 (device_id 등록 + 서버 발급 토큰으로 대체)
- 푸시 알림
- 인스타그램 외 출처(네이버지도 / 구글맵 / 수동 입력) — 미결 확정 시 별도 태스크로 편입

### 2.1 인증·보안 모델 (MVP)

로그인이 없으므로, 무엇을 보호하고 무엇을 감수하는지를 명시해 둔다.

**보호 대상 자산**

- 방 정보와 멤버 목록, 방에 저장된 핀·장소
- 프로필(닉네임·프로필 이미지)
- 핀 코멘트

**인증 방식**

- `device_id`는 **최초 유저 등록에만 사용**하고, 이후 요청의 신원 증명 수단으로 신뢰하지 않는다.
  - `device_id`는 클라이언트가 임의 값으로 제출할 수 있으므로, 이를 그대로 식별자로 받으면 타인의 방·핀·프로필을 조회·수정할 수 있다.
- 등록 응답으로 **서버가 발급한 불투명(opaque) 토큰**을 내려주고, 이후 모든 요청은 `Authorization: Bearer <token>`으로 인증한다. 서버는 토큰으로만 요청 유저를 결정한다.
- 방 스코프 리소스(핀·코멘트·멤버)는 요청 유저의 `room_members` 소속 여부를 검증한 뒤 처리한다.

**MVP에서 감수하는 위험 (allowed risk)**

- 토큰이 유출되면 해당 유저로 위장 가능하다. 토큰 회전·폐기·다중 기기 세션 관리는 MVP 비목표이며, 계정 시스템 도입 시 다룬다.
- 앱 삭제·재설치 또는 기기 변경 시 토큰이 소실되면 기존 유저로 복구할 수 없고 새 유저가 된다. (복구 수단 = 계정 시스템, MVP 비목표)
- 초대 링크를 입수한 사람은 누구나 방에 합류할 수 있다. 링크 자체가 방의 접근 권한이다.
- 저장되는 데이터에 민감정보(연락처·결제·위치 이력)를 포함하지 않는 것을 전제로 한다.

## 3. 핵심 사용자 시나리오

디자인은 두 가지 진입 케이스를 구분한다.

### Case 1: 최초 초대자 (방을 만드는 사람)

1. 온보딩·튜토리얼: 프로필 설정(닉네임) → 공동방 만들기(이름·색상) → 친구 초대 → SNS 공유 연습 → 완료
2. 인스타그램에서 마음에 드는 장소 게시물을 발견 → 공유 시트에서 쏙핀 선택 → 저장할 방 선택 → 완료 피드백
3. 홈에서 카드 덱으로 저장된 장소를 탐색, 지도/리스트에서 확인
4. 친구들과 장소 상세에서 코멘트로 의견 교환

### Case 2: 초대받은 사람

1. 초대 링크(`ssokpin.app/r/{code}`)로 진입 → 프로필 설정 → 방 합류
2. 이후 흐름은 Case 1과 동일 (링크 저장, 탐색, 코멘트)

## 4. 기능 정의

Figma 섹션 번호([000]~[006])를 기준으로 한다.

### [000] 공유 유입 (공동방 생성 플로우)

외부 앱(인스타그램 등)에서 시스템 공유 시트로 링크를 쏙핀에 공유하는 핵심 유입 경로.

- 공유 버튼 클릭 → 공유 대상(쏙핀) 선택 → 시스템 공유 시트 표출 → 저장 완료 피드백
- 백엔드 관점: 링크 수신 → `sources` 등록(`original_url` 유니크로 재유입 시 재사용) → 스크래핑 → AI 장소 추출 → 지오코딩(Kakao/Google) → `places` dedup 저장 → 선택한 방에 `pins` 생성
- 같은 방에 같은 장소는 중복 핀되지 않는다. (`pins (room_id, place_id)` 유니크)

### [001] 튜토리얼 (온보딩)

- **프로필 설정**: 닉네임(최대 10자, "친구들이 뭐라고 부르면 좋을까요?"), 프로필 이미지
- **공동방 만들기**: 방 이름(최대 20자), 색상(팔레트 5색 중 선택)
- **친구 초대**: 초대 링크 공유
- **SNS 공유 연습**: "아래 공유 버튼을 눌러서 연습해보세요" — [000] 플로우를 튜토리얼 안에서 체험
- 백엔드 관점: device_id 기반 유저 생성, 방 생성, 초대 코드 발급

### [002] 홈 탭 (카드 덱 탐색)

방 하나를 골라 그 방의 핀을 카드 덱으로 탐색하는 메인 화면.

- 카드는 **10개** 노출 (디자인 주석: "보여주는 카드는 10개로 합니다")
- 정렬 3종: **꾹Pick / 최신순 / 가까운순** — "카드 정렬 값 = 모든 값은 그룹 내의 순위로 정렬"
- 인터랙션: 오른쪽 스와이프 = 넘기기, 다시 왼쪽 스와이프 = 복구
- 10개 탐색 완료 시: 플로팅 버튼 클릭하면 10개 재생성, 무시하면 자연스럽게 다음 방으로 전환
- 방 변경: 방 선택 시트에서 전환, 전환 시 방 소개 툴팁 3초 노출 후 사라짐
- 데이터 없을 때: empty state ("아직 꾹 눌러둔 장소가 없어요")

### [003] 저장탭 (방 리스트)

지도 위 바텀시트(peek / half / full 3단)로 방 리스트를 보여준다.

- 상태 구분: 개인방만 존재 / 공동방 N개 이상 존재
- 방 리스트에서 방을 선택하면 [004] 방 상세로 진입

### [004] 방 상세

방에 저장된 핀 목록과 방 단위 액션. 바텀시트 3단(peek / half / full).

- **핀 리스트**: 방의 핀들을 리스트로 확인
- **다른 방에 공유**: 핀을 다른 방으로 복제, 완료 시 토스트 피드백
- **링크로 장소 직접 추가**: 앱 안에서 링크를 붙여넣어 [000]과 동일한 파이프라인으로 핀 추가
- **친구 초대**: 초대 링크 공유
- **방 편집**: 이름·색상 변경

### [005] 지도뷰 & 장소 상세

- **지도뷰**: 방의 핀들을 지도 위에 표시
- **장소 상세**: 장소 정보(이름·주소·카테고리 등) + 출처 링크 + 코멘트 (half / full)
- **코멘트**: 방 멤버가 핀에 코멘트 작성 (empty state: "아직 코멘트가 없어요!")
- **다른 방에 공유 / 새 방 만들기**: 장소 상세에서 바로 다른 방으로 공유하거나, 새 공동방을 만들어 공유 (미가입 상태면 프로필 설정 포함)

### [006] 친구 초대

- 초대 링크(`ssokpin.app/r/{code}`) 생성·공유
- 링크로 진입한 사용자는 프로필 설정 후 해당 방의 멤버가 된다 (Case 2 온보딩)
- 중복 참여는 불가 (`room_members (room_id, user_id)` 유니크)

## 5. 데이터 모델 개요

PR #44 기준 8개 테이블. (리뷰 중 — 확정 전이며, 아래는 요약)

| 테이블 | 역할 | 비고 |
|---|---|---|
| `users` | device_id 기반 사용자 | `device_id` 유니크, 닉네임(10자)·프로필 이미지 |
| `rooms` | 방 | `type`: `personal`(개인방) / `shared`(공동방), 이름(20자)·색상(팔레트 hex)·`invite_code` 유니크 |
| `room_members` | 방 멤버십 | `(room_id, user_id)` 유니크로 중복 참여 방지 |
| `sources` | 출처 링크 | `type`: instagram / naver_map / google_map / manual, `original_url` 유니크(재유입 시 재사용) |
| `places` | 장소 마스터 | `(provider, provider_place_id)` 유니크로 dedup (provider: kakao / google) |
| `place_sources` | 장소↔출처 N:M | 같은 장소가 여러 출처에서 유입될 수 있음 |
| `pins` | 방에 저장된 장소 | `(room_id, place_id)` 유니크, `last_accessed_at`으로 최근 접근 추적 |
| `pin_comments` | 핀 코멘트 | 작성자가 방 멤버인지는 애플리케이션 레벨에서 검증 |

## 7. 미결 사항 (Open Questions)

확정되지 않아 관련 피쳐 개발 전 결정이 필요한 항목.

1. **인스타그램 외 출처의 MVP 포함 여부**: 현재 스크래퍼는 인스타그램만 구현되어 있어 목표를 인스타그램으로 한정했다. 아래 3종은 포함 여부 확정 필요하며, 포함 시 각각 별도 태스크로 정의한다.
   - **네이버지도 / 구글맵**: 링크 분석 파이프라인은 동일하나 출처별 스크래퍼·파서 추가 필요.
   - **수동 입력**: 링크가 없으므로 **파이프라인이 아예 다르다.** 스크래핑·AI 추출 단계 없이 장소 검색(`modules/place`) 결과를 바로 선택하는 별도 입력 계약이 필요하다. `sources.type: manual`의 `original_url` 처리 방식(nullable 허용 여부)도 함께 확정해야 한다.
2. **꾹Pick 정렬 기준**: 디자인 주석에 "중복 저장 데이터로 정렬"과 "코멘트수로 정렬"이 혼재되어 있다. 어느 기준인지(혹은 복합 기준인지) 확정 필요. 데이터로는 `place_sources` 수(중복 저장) / `pin_comments` 수(코멘트) 모두 산출 가능.
3. **`pins.last_accessed_at`의 사용자별 분리**: 현재는 핀 단위 단일 값. 홈 카드 탐색이 사용자별이라면 사용자별 접근 기록(`pin_accesses` 등)이 필요할 수 있다. PR #44 리뷰에서도 스펙 확정 후 후속 반영으로 미뤄둔 상태.
4. **코멘트 수정/삭제 정책**: soft delete 여부 등 미정 (PR #44 리뷰 노트).

## 8. API 설계 초안 (RESTful Draft)

경로·메서드 수준의 초안이다. 요청/응답 스키마, 에러 코드, 페이지네이션 상세는 각 피쳐 PR에서 확정한다.

**공통 규칙**

- 베이스 경로: `/api/v1` (기존 `PlaceController` 컨벤션 유지)
- 인증: `Authorization: Bearer <token>` — 유저 등록(`POST /users`)과 초대 미리보기(`GET /invitations/{code}`)를 제외한 전 엔드포인트 필수
- 리소스는 복수형 명사, 동작은 HTTP 메서드로 표현한다. 상태 변경 기록처럼 명사화가 자연스러운 동작은 하위 컬렉션(`/accesses`)으로 표현한다.
- 부분 수정은 `PATCH`, 컬렉션 추가는 `POST`

### 유저

| Method | Path | 설명 | 화면 |
|---|---|---|---|

| Method | Path | 설명 | 화면 |
|---|---|---|---|
| `POST` | `/api/v1/link-analyses` | 링크 분석 — 스크래핑 → AI 추출 → 지오코딩 → 장소 후보 반환 | [000] [004] |
| `POST` | `/api/v1/rooms/{roomId}/pins` | 방에 핀 생성 (신규 저장 / 다른 방에서 복제 겸용) | [000] [004] [005] |
| `GET` | `/api/v1/rooms/{roomId}/cards` | 홈 카드 피드 조회 (10개) | [002] |
| `GET` | `/api/v1/pins/{pinId}` | 장소(핀) 상세 — 장소 정보 + 출처 링크 + 코멘트 수 | [005] |
| `POST` | `/api/v1/pins/{pinId}/accesses` | 핀 접근 기록 (`last_accessed_at` 갱신) | [002] |

**세부 계약 메모**

- `POST /link-analyses`: 기존 `POST /api/v1/place/places`(`place.controller.ts`)가 동일 역할을 하므로, 이 경로로 정리하며 흡수한다. MVP 지원 출처는 인스타그램 링크. (미결 1)
- `POST /rooms/{roomId}/pins`: body의 생성 방식으로 두 경로를 모두 수용한다.
  - `{ "from": "extraction", "sourceId": ..., "place": {...} }` — 링크 분석 결과 저장
  - `{ "from": "pin", "pinId": ... }` — 다른 방의 핀 복제 ([004] [005] "다른 방에 공유")
  - 같은 방에 같은 장소가 이미 있으면(`pins (room_id, place_id)` 유니크) 신규 생성 대신 기존 핀을 반환한다. 정확한 상태 코드(200 vs 409)는 구현 PR에서 확정.
- `GET /rooms/{roomId}/cards`: `?sort=pick|recent|nearby`, `nearby`는 `lat`/`lng` 필수. 10개 재생성은 이미 본 카드를 제외하기 위한 커서/제외 목록 파라미터로 처리한다. `pick` 정렬 기준은 미결 2.
- `POST /pins/{pinId}/accesses`: 접근을 하위 컬렉션으로 둔 이유는, 사용자별 접근 기록으로 확장(미결 3)될 때 경로 변경 없이 `pin_accesses` 저장으로 바뀔 수 있기 때문이다.

## 9. 기능별 태스크 리스트

하나의 태스크 = 하나의 PR 단위. 클라이언트(iOS/Android) 작업은 제외하고 백엔드 기준으로 리스트업한다.

### 공통 / 기반

- **기반 > DB > MVP 스키마 정의 및 마이그레이션** — *진행 중 (PR #44)*
  - 8개 테이블 Drizzle 스키마 + 초기 마이그레이션. 리뷰 반영 후 develop 스키마 적용.
- **유저 > API > device_id 기반 유저 등록·식별** — `POST /users`, `GET·PATCH /users/me`
  - device_id로 유저 upsert(최초 진입 시 생성) + 인증 토큰 발급, 토큰으로 요청 유저를 식별하는 가드/데코레이터. (→ 2.1 인증·보안 모델)
  - 프로필 설정(닉네임 10자, 프로필 이미지) 등록·수정 포함.

### [000] 공유 유입 · [004] 링크로 장소 직접 추가

- **링크 유입 > API > 링크 분석 (장소 추출)** — `POST /link-analyses`
  - 링크 수신 → `sources` 등록(`original_url` 재유입 시 재사용) → 스크래핑 → AI 장소 추출 → 지오코딩(Kakao/Google) → 장소 후보 반환.
  - 기존 인프라(scraper·ai·geocoder·place) 조합. **MVP 지원 출처는 인스타그램 링크로 한정**하고, 기존 `POST /api/v1/place/places`를 이 경로로 정리·흡수한다.
- **핀 > API > 핀 생성 (방에 장소 저장)** — `POST /rooms/{roomId}/pins`
  - 추출된 장소를 `places`에 dedup 저장(`provider, provider_place_id`), `place_sources` 연결, 선택한 방에 `pins` 생성.
  - 같은 방 중복 핀(`room_id, place_id` 유니크) 시 응답 정책 포함.

### [001] 튜토리얼 · [006] 친구 초대

- **방 > API > 방 생성** — `POST /rooms`
  - 공동방 생성(이름 20자·색상·`invite_code` 발급). 온보딩 시 개인방(`type: personal`) 자동 생성 규칙 포함.
- **방 > API > 초대 코드로 방 참여** — `GET /invitations/{code}`, `POST /rooms/{roomId}/members`
  - 초대 코드로 방 조회(미리보기, 인증 불필요) + `room_members` 합류. 중복 참여 시 멱등 처리.

### [002] 홈 탭

- **홈 > API > 카드 피드 조회** — `GET /rooms/{roomId}/cards`
  - 방별 핀 카드 10개 조회. 정렬 3종: 꾹Pick(기준 미결 — Open Questions 2) / 최신순 / 가까운순(좌표 파라미터).
  - 탐색 완료 후 10개 재생성 요청 처리(이미 본 카드 제외).
- **핀 > API > 핀 접근 기록 (last_accessed_at 갱신)** — `POST /pins/{pinId}/accesses`
  - 카드 탐색(넘기기) 시 접근 시각 갱신. 사용자별 분리 여부는 미결(Open Questions 3)로, 확정 시 스키마 후속 반영.

### [003] 저장탭

- **방 > API > 방 리스트 조회** — `GET /rooms`
  - 유저가 속한 방 목록(개인방/공동방 구분, 핀 수 등 메타 포함).

### [004] 방 상세

- **방 > API > 방 상세 조회** — `GET /rooms/{roomId}`
  - 방 정보 + 핀 리스트(지도뷰용 좌표 포함).
- **핀 > API > 다른 방에 공유 (핀 복제)** — `POST /rooms/{roomId}/pins` (`from: "pin"`)
  - 핀을 대상 방으로 복제. 대상 방에 이미 같은 장소가 있는 경우 응답 정책 포함.
- **방 > API > 방 편집** — `PATCH /rooms/{roomId}`
  - 이름·색상 수정.

### [005] 지도뷰 & 장소 상세

- **핀 > API > 장소(핀) 상세 조회** — `GET /pins/{pinId}`
  - 장소 정보(이름·주소·카테고리 등) + 출처 링크 + 코멘트 목록/수.
- **코멘트 > API > 핀 코멘트 작성·조회·삭제** — `GET·POST /pins/{pinId}/comments`, `DELETE /pins/{pinId}/comments/{commentId}`
  - 방 멤버 검증(애플리케이션 레벨). 수정/삭제 정책은 미결(Open Questions 4)로, 확정 후 반영.

### INFRA / 후속

- **INFRA > Script > 마이그레이션 SQL `"public".` 프리픽스 제거 자동화**
  - `db:generate` 후처리 스크립트 (PR #44 리뷰 노트의 후속 작업).

> 참고: 방 나가기/삭제, 핀 삭제 플로우는 현재 디자인 섹션에서 확인되지 않아 태스크에서 제외했다. 스펙 확인 후 추가한다.
>
> 참고: 인스타그램 외 출처(네이버지도 / 구글맵 / 수동 입력)는 미결 1 확정 후 태스크를 추가한다. 네이버지도·구글맵은 링크 분석 태스크의 확장이지만, 수동 입력은 스크래핑·AI 추출을 거치지 않는 별도 입력 계약이므로 독립 태스크가 된다.
