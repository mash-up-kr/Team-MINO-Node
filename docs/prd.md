## 1. 서비스 개요

**꾹은 SNS·지도 앱에서 발견한 장소 링크를 방(Room)에 모아두고, 친구들과 함께 다음 약속 장소를 고르는 서비스다.**

> "카톡방에 흘러간 링크, 그만 찾아 헤매세요. 방에 모아두면 약속 잡을 때 바로 꺼내 써요."
> "'여기 어때?'는 이제 그만. 친구가 들어오면 저장한 장소가 한눈에 모여요. 다음 약속 장소, 여기서 같이 골라요."

### 해결하는 문제

- 인스타그램 등에서 발견한 가고 싶은 장소가 카톡방·북마크에 흩어져 있어, 약속을 잡을 때 다시 찾기 어렵다.
- 장소 링크(게시물)에는 구조화된 장소 정보(이름·주소·좌표)가 없어, 지도에서 다시 검색하는 수고가 필요하다.
- 모임 단위로 장소 후보를 모으고 의견을 나눌 공간이 없다.

### 핵심 컨셉

- **공유 시트로 유입**: 인스타그램에서 시스템 공유 시트를 통해 링크를 꾹으로 보내면, 장소가 자동으로 추출되어 방에 핀으로 저장된다. 추출에는 시간이 걸리므로 **접수는 즉시 응답하고, 결과 푸시는 중복·실패 시에만 발송한다.** (PR 리뷰 확정 → [4장 [000]](#000-공유-유입))
- **방(Room) 중심 구조**: 모든 핀은 방에 속한다. 온보딩 시 생성되는 개인방("내 방")과, 초대 코드로 친구를 모으는 공동방이 있다.
- **카드 탐색**: 홈에서 방의 핀을 카드 덱으로 탐색하고("꾹 눌러둔 장소, 다시 꺼내볼까요?"), 지도·리스트로도 확인한다. 카드 소비 상태는 **개인별**이라 다른 멤버에게 영향을 주지 않는다. (디자인 리뷰 확정)
- **공통 프로필 1회 설정**: 닉네임·프로필 이미지는 최초 진입 시 1회만 받고 모든 방에 공통 적용한다. 방별 닉네임/프로필 분리는 하지 않는다. (디자인 리뷰 확정)
- **로그인 없는 MVP**: 계정 가입 없이 `device_id`로 최초 1회 등록한다. 인증 방식 상세는 PRD 범위 밖이다. (→ [2.1 인증·보안](#21-인증보안-별도-설계))

## 2. 목표 / 비목표

### 목표 (MVP 범위)

- 링크 공유 → 장소 추출 → 핀 저장의 핵심 루프가 **인스타그램 링크** 기준으로 동작한다.
- 처리 결과(성공 / 중복 저장 / 오류)를 사용자에게 안내한다. **푸시 알림은 중복·실패 시에만 발송한다.** (PR 리뷰 확정 — 알림 구성 상세는 TBD, → [[006] 알림함](#006-알림함))
- 개인방·공동방을 만들고, 초대 링크(e.g, `gguk.org/r/{code}`)로 친구가 합류할 수 있다.
- 방의 핀을 홈 카드 덱 / 지도 뷰 / 리스트로 탐색하고, 장소 상세에서 코멘트를 나눌 수 있다.
- 핀을 다른 방으로 공유(복제)할 수 있다.
- **방 나가기**와 **방장 위임**이 가능하다.
- 마이페이지에서 약관 확인·테마 변경·알림/위치 설정·닉네임/프로필 수정이 가능하다.

### 비목표 (MVP에서 다루지 않음)

- 소셜 로그인·계정 시스템 (device_id 기반 등록으로 대체 — 인증 설계는 별도 문서)
- **인스타그램 외 출처**(네이버지도 / 구글맵 / 수동 입력) — MVP 1단계 미반영 (디자인 리뷰 확정)
- **장소 직접 추가** — 구현 비용 대비 사용자 가치가 낮아 스펙 아웃. 유입은 인스타그램 공유 시트로 일원화한다. (디자인 리뷰 확정)
- **명시적 방 삭제 기능** — 방을 폭파시키는 개념 대신 `방 나가기 + 방장 위임` 구조로 간다. 단, **방장이 마지막 멤버로 나가는 경우에는 방을 삭제(soft delete) 처리한다.** (PR 리뷰 확정)
- **계정 탈퇴** — 디바이스 중심 구조라 우선순위가 낮다. (디자인 리뷰 확정)
- 방별 닉네임/프로필 분리

> 참고: 푸시 알림은 이전 버전에서 비목표였으나, 링크 처리 지연 때문에 **결과 전달의 유일한 수단**이 되어 목표로 승격됐다. (디자인 리뷰 확정) 이후 PR 리뷰에서 발송 대상이 **중복·실패로 한정**됐다.

### 2.1 인증·보안 (별도 설계)

**인증 설계(토큰 스펙·발급·저장·재등록 처리 등)는 PRD 범위에서 제외하고 별도 문서에서 다룬다.** (PR 리뷰 확정) 이 문서에는 전제만 남긴다.

- 로그인 없는 구조: `device_id` 기반으로 최초 1회 등록하고, 서버가 내려주는 식별 수단으로 이후 요청 유저를 식별한다(잠정: Bearer 토큰). 상세 계약은 별도 설계에서 확정한다.
- 보호 대상 자산: 방 정보·멤버 목록·핀·장소, 프로필(닉네임·이미지), 핀 코멘트, 알림 내역.
- 방 스코프 리소스(핀·코멘트·멤버·알림)는 요청 유저의 `room_members` 소속 여부를 검증한 뒤 처리한다.
- 앱 삭제·재설치 또는 기기 변경 시 기존 유저로 복구할 수 없다. 새 유저로 시작하며, 이전에 속한 방은 초대 링크로 다시 합류한다. (복구 수단 = 계정 시스템, MVP 비목표)
- 초대 링크를 입수한 사람은 누구나 방에 합류할 수 있다. 링크 자체가 방의 접근 권한이다.

## 3. 핵심 사용자 시나리오

디자인은 두 가지 진입 케이스를 구분한다.

### Case 1: 최초 초대자 (방을 만드는 사람)

1. 스플래시에서 위치·알림 권한 요청 (PR 리뷰 확정 — **초반 진입 구간에서 요청**)
2. 온보딩: 프로필 설정(닉네임 + 프로필 이미지) → 공동방 만들기(이름·색상) → 친구 초대 → SNS 공유 연습 → 완료
3. 인스타그램에서 마음에 드는 장소 게시물을 발견 → 공유 시트에서 꾹 선택 → 저장할 방 선택 → **접수 피드백** → 처리 결과 안내(푸시는 중복·실패 시)
4. 홈에서 카드 덱으로 저장된 장소를 탐색, 지도/리스트에서 확인
5. 친구들과 장소 상세에서 코멘트로 의견 교환

### Case 2: 초대받은 사람

1. 초대 링크(`gguk.org/r/{code}`)로 진입 → **닉네임·프로필 설정 → 초대 수락(방 합류)** 순서로 진행한다. (PR 리뷰 확정)
2. 이후 흐름은 Case 1과 동일 (링크 저장, 탐색, 코멘트)

> 초대 링크의 **유효기간은 무제한**이고, 초대장에 **거절 개념은 없다**. 합류가 완료되면 **방 멤버 전원에게 푸시 알림을 발송한다**. (PR 리뷰 확정)
>
> 온보딩 "건너뛰기" 시 도달 지점, 인스타그램 → 앱 유입 과정, 초대 링크 → 설치 → 진입 과정은 **화면 단위 디자인과 별개로 전체 플로우 문서가 필요**하다는 것이 회의 결론이다. 확정되면 이 장을 갱신한다.

## 4. 기능 정의

Figma **새 보드**(node `1512:70762`)의 섹션 번호 [000]~[007]을 기준으로 한다. 구 보드와 번호가 다르니 주의: [000] 튜토리얼(공유 플로우) / [001] 공동방 생성(온보딩) / [002] 홈 / [003] 방 리스트 / [004] 방 상세 / [005] 장소 상세 / [006] 알림 / [007] 마이페이지.
각 절의 **백엔드 관점**은 해당 화면이 서버에 요구하는 동작을 정리한 것으로, [8장 API 초안](#8-api-설계-초안-restful-draft)·[9장 태스크](#9-기능별-태스크-리스트)와 대응된다.

### [000] 공유 유입

인스타그램에서 시스템 공유 시트로 링크를 꾹에 공유하는 핵심(이자 유일한) 유입 경로. 새 보드의 [000] 튜토리얼 섹션이 이 플로우의 화면(공유 버튼 → 공유 대상 → 공유 시트 → 완료 피드백)을 담고 있다.

- 공유 버튼 클릭 → 공유 대상(꾹) 선택 → 저장할 방 선택 → **접수 피드백**
- 스크랩 → LLM 장소 추출 → 지오코딩에 시간이 걸리므로, **응답 완료까지 기다렸다가 토스트를 띄우는 방식은 쓰지 않는다.** 즉시 가능한 범위(접수됨)까지만 피드백한다. (디자인 리뷰 확정)
- 결과 유형: 성공 / 중복 저장 / 오류. **푸시는 중복·실패 시에만 발송한다.** (PR 리뷰 확정) 성공 결과의 안내 방식과 알림함 구성은 TBD. (→ [[006] 알림함](#006-알림함))

**백엔드 관점**

1. 링크 접수: `original_url` 정규화 → `sources` 조회·등록(살아있는 행 기준 유니크이므로 재유입 시 기존 행 재사용) → Cloud Tasks 큐에 enqueue 후 **즉시 202 응답**(접수만, `jobId`는 내려주지 않는다).
2. 백그라운드 처리(Cloud Tasks 워커): 스크래핑(`infrastructures/scraper`) → AI 장소 추출(`infrastructures/ai`) → 지오코딩(`infrastructures/geocoder`, Kakao/Google).
3. 저장: `places`에 `(provider, provider_place_id)` 기준 dedup upsert → `place_sources` 연결(`(place_id, source_id)` 살아있는 행 유니크라 재유입 시 기존 연결 재사용) → 선택한 방에 `pins` 생성.
4. 중복 판정: 같은 방에 같은 장소가 이미 있으면(`pins (room_id, place_id)` 살아있는 행 유니크) 새 핀을 만들지 않고 **중복 결과**로 처리한다.
5. 결과 알림: 처리 종료 시 결과 유형별 알림 레코드를 남기고, **중복·실패인 경우 푸시를 발송한다.** 중복인 경우 **기존 핀으로 이동할 수 있는 참조(방·핀 식별자, 최초 저장 시각)** 를 함께 담는다. (→ [[006] 알림함](#006-알림함))
6. 실패 처리: 재시도·백오프는 **Cloud Tasks 재시도 정책에 맡긴다**(DB에 상태를 남기지 않는다). 최종 실패 시 오류 알림을 남기고 푸시를 발송한다.
7. **한 게시물에서 장소가 여러 개 추출되는 경우**(핀 N개 생성, 일부만 성공/중복인 부분 성공, 푸시 발송 횟수)의 정책은 오류 상황을 상세 정의한 뒤 프디팀과 확정한다. (PR 리뷰 결론 → [미결 4](#7-미결-사항-open-questions))

### [001] 온보딩 (공동방 생성)

새 보드의 [001] 공동방 생성 섹션: 프로필 설정 → 공동방 만들기 → 친구 초대.

- **프로필 설정**: 닉네임 + **프로필 이미지**를 함께 받는다.
  - 닉네임 정책 (안드 스펙 정합으로 갱신): **한글/영문만 2자 이상 15자 이내 — 공백·숫자·특수문자 불가.** 상한 15자는 서버(DB `varchar(15)`) 계약이며, 클라이언트는 상한 없이 서버 거절을 저장 실패로 노출한다.
  - "모든 방에 사용할래요?" 체크박스는 **제거**한다. 닉네임·프로필은 최초 1회 공통 설정이다. (디자인 리뷰 확정)
  - 프로필 노출 지점이 많아(초대된 사람 표시, 장소 추가한 사람 표시) 기본 아바타 고정값보다 초기 수집이 낫다는 판단.
- **공동방 만들기**: 방 이름·설명·색상(팔레트 13색 키 중 선택 — snake_case, 실제 색 매핑은 클라이언트)
  - 방 이름 정책 (PR 리뷰 확정): **최소 제한 없음, 최대 15자, 중복 허용, 앞뒤 공백 제거.** 방 설명은 **30자 이내**(기획 확정). 글자 수는 **grapheme 단위**로 센다(클라이언트와 동일).
- **친구 초대**: 초대 링크 공유
- **SNS 공유 연습**: "아래 공유 버튼을 눌러서 연습해보세요" — [000] 플로우를 튜토리얼로 체험 (새 보드 [000])
- **권한 요청**: 위치·알림 권한은 **초반 진입 구간에서 요청한다.** (PR 리뷰 확정)

**백엔드 관점**

- `device_id`로 유저 생성 후 닉네임·프로필 이미지를 같은 흐름에서 등록한다. 등록·인증 계약 상세는 별도 인증 설계에서 확정한다. (→ [2.1](#21-인증보안-별도-설계))
- **개인방 자동 생성은 `POST /users` 등록 흐름 안에서 함께 처리한다.** (PR 리뷰 확정) 등록 응답에 개인방 정보를 포함할지는 상세 PR에서 정한다.
- 개인방(`rooms.type = personal`, 표시명 "내 방")의 **색상은 프디팀이 추후 결정한다**(`rooms.color`가 notNull이므로 임시로 랜덤 부여 후 수정 가능하게 하는 안이 제안됨). (→ [미결 5](#7-미결-사항-open-questions))
- 공동방 생성 시 생성자가 `rooms.owner_id`가 된다. 초대 코드는 방 생성과 분리돼 `invitations`가 관리한다.
- 프로필은 제공 아바타 선택 방식으로, 아바타 객체(`{ color }` 색상 키, 추후 필드 확장)를 `users.avatar`(jsonb)에 통째 보관한다. 실제 색 매핑은 클라이언트 담당이며 별도 이미지 업로드는 없다.
- 알림 권한 허용 시 푸시 토큰을 등록받아야 한다. ([000] 결과 알림의 전제)

### [002] 홈 탭 (카드 덱 탐색)

방 하나를 골라 그 방의 핀을 카드 덱으로 탐색하는 메인 화면.

- **덱은 최대 10장**이다. 후보가 10개보다 적으면 있는 만큼만 채운다(핀 4개면 4장). 저장 장소가 0개인 방은 건너뛴다.
- 인터랙션: 오른쪽 스와이프 = 넘기기, 다시 왼쪽 스와이프 = 복구
- **덱 소진은 클라이언트 로컬 상태로 다룬다.** 스와이프는 서버에 기록하지 않으므로, 넘긴 카드를 덱에서 빼는 것도 클라이언트가 판단한다.
- **큐레이션 상태는 개인별**이다. 카드를 넘기거나 소비해도 다른 멤버에게 영향이 가지 않는다. (디자인 리뷰 확정)
- **카드 액션 메뉴**: 카드의 더보기 버튼에 `다른 방 저장`이 있다.
  - 이전 서술("카드 내 점 3개 메뉴는 제거한다")은 **낡았다.** 이 화면의 카드에는 메뉴가 있다.
- **첫 진입 튜토리얼**: 클릭하면 방을 바꿀 수 있다는 것, 카드를 좌우로 스와이프할 수 있다는 것을 안내한다. **별도 화면 단위**로 설계한다. (캐릭터 외형 미정)
- **현재 선택된 방은 고정 라벨로 노출**한다는 것이 디자인 리뷰 결정이었으나, **새 보드에는 "방 변경 시 툴팁 유지" 화면이 그대로 남아 있다** — 재확인 필요. (→ [미결 8](#7-미결-사항-open-questions))
- 카드 클릭 시 **장소 상세로 이동한다는 점을 명확히 표기**한다.
- 데이터 없을 때: empty state의 CTA는 "첫 장소 저장하기"가 아니라 **"방 만들기"**다. 장소를 저장하려면 방이 먼저 있어야 하기 때문. (디자인 리뷰 확정)

#### 정렬 기준 — 후보 10장을 고른다

상단 칩으로 고르며 기본값은 `꾹 Pick`이다. 각 기준이 조건과 정렬을 함께 정하고, 그 결과 상위 10장이 덱의 후보가 된다.

| 칩 | 조건 | 정렬 |
|---|---|---|
| `꾹 Pick` (기본) | 없음 (방 전체) | **묵힘** 오래된 순 |
| `최신순` | 저장일이 **최근 14일 이내** | 저장일 최신순 |
| `가까운순` | 요청 좌표 기준 **반경 3km 이내** | 거리 가까운 순 |

- **묵힘 = `coalesce(마지막으로 열어본 시점, 저장일)`이다.** 한 번도 열어본 적 없는 핀은 저장 시점을 쓴다.
- 스와이프는 서버에 기록하지 않는다. 그래서 묵힘을 되돌리는 것은 **카드를 눌러 장소 상세로 들어간 클릭**뿐이다. 스쳐 지나간 카드는 아직 안 본 것으로 남는다.
- 열어본 핀은 묵힘이 갱신돼 `꾹 Pick` 후보에서 뒤로 밀린다. 그래서 **"이미 본 카드 제외" 같은 별도 조건이 필요 없다.**

#### 덱 구성 — 후보 10장에 라벨을 붙인다

라벨은 덱을 뽑는 단위가 아니라 **뽑힌 10장에 붙이는 표시**다. 아래 순서대로 배정하며, 앞 라벨이 가져간 장소는 제외된다.

| 순 | 라벨 | 자격 | 정렬 | 정원 |
|---|---|---|---|---|
| 1 | `가볼 만한 곳` | 없음 | 묵힘 오래된 순 | 4 |
| 2 | `여럿이 저장한 곳` | 저장된 방 **2곳 이상** | 저장된 방 수 많은 순 | 2 |
| 3 | `이야기 많은 곳` | 코멘트 **1건 이상** | 코멘트 수 많은 순 | 2 |
| 4 | `친구들이 많이 본 곳` | 클릭 **1회 이상** | 클릭 수 많은 순 | 2 |

- **자격 미달로 남은 자리는 `가볼 만한 곳`이 흡수한다.** 자격 조건이 없는 유일한 라벨이라 항상 채울 수 있고, 덕분에 후보가 10장이면 덱도 10장이 된다.
- 그래서 지표가 전부 0인 신규 방은 **10장 모두 `가볼 만한 곳`**이 된다. 짧은 덱을 내거나 코멘트 0인 장소에 `이야기 많은 곳`을 붙이는 것보다 낫다고 본다.
- 한 장소는 한 라벨에만 속한다. 동점은 묵힌 순으로 깬다.
- **응답은 후보 정렬 순서를 그대로 유지한다.** 라벨별로 묶어 내리지 않는다.

#### 자동 전환

- 덱을 소진하면 **같은 정렬 기준으로 다음 방**의 덱을 이어 노출한다. 저장 장소가 0개인 방은 건너뛴다.
- 현재 정렬에서 더 볼 방이 없으면 `꾹 Pick` → `최신순` → `가까운순` 순으로 **정렬을 자동 전환**한다. 후보가 0건인 정렬은 건너뛴다.
- `가까운순`까지 모두 소진했을 때만 완료 화면(`꾹 눌러둔 장소를 모두 둘러봤어요`)으로 전환한다.
- 앱 최초 실행은 개인방(`내 장소`)에서 시작하고, 이후에는 **마지막으로 본 방**에서 시작한다.

**백엔드 관점**

- 카드 피드는 `GET /rooms/{roomId}/cards`로 조회하며 `sort`(기본 `ggukPick`)를 받는다. `sort=nearby`는 요청 좌표가 필요하다.
- 응답의 각 카드는 `labelGroup`을 포함한다. **라벨 판정은 서버가 한다** — 클릭수·코멘트수·중복 저장 수는 서버에만 있다.
- **페이지네이션도, 재생성 계약도 두지 않는다.** 매 호출마다 새로 계산해 10장을 돌려주고, 다시 부르는 시점은 클라이언트가 정한다.
- `pin_accesses`는 **묵힘 계산과 `친구들이 많이 본 곳` 클릭수 집계** 두 곳에 쓰인다. 같은 테이블을 최신성과 빈도로 각각 읽는 셈이라 혼동하지 않도록 주의한다.
- **자동 방 전환에 별도 API는 필요 없다.** 클라가 `GET /rooms`의 `pinCount`로 다음 방을 고르고 그 방의 `cards`를 부른다.
- 카드에 등록자 아바타를 표시하려면 `pins.created_by` 조인이 필요하다. 작성자가 탈퇴/삭제된 경우의 표시 방식(스키마상 참조는 유지됨)을 정해야 한다.
- 반경 필터는 PostGIS 없이 **바운딩 박스 + 하버사인**으로 계산한다. 데이터가 늘면 `places(lat, lng)` 인덱스를 검토한다.
### [003] 방 리스트 (저장탭)

지도 위 바텀시트(peek / half / full 3단)로 방 리스트를 보여준다.

- 상태 구분: 개인방만 존재 / 공동방 N개 이상 존재
- 방 리스트에서 방을 선택하면 [004] 방 상세로 진입
- **공동방 생성 유도 바텀시트** (새 보드 003-3): 공동방을 만들지 않고 재접속한 사용자가 저장 탭을 클릭하면 노출한다. 공동방을 한 번이라도 만들면 이후 노출하지 않는다.
- **바텀시트 높이는 픽셀 고정값이 아니라 화면 높이 대비 비율로 정의**한다. 기기별 높이 차이를 고려한 비율 기반 명세가 필요하다. (디자인 리뷰 확정)
- **방 생성 CTA 2개 운영 유지**: "공동방 만들기" CTA와 플러스 버튼이 함께 있는 구조를 유지한다. CTA는 초기 사용자를 위한 일회성 강조 장치이며, 방이 많아지면 사라진다. (디자인 리뷰 확정)

**백엔드 관점**

- 유저가 속한 방 목록을 반환한다. 개인방/공동방 구분, 핀 수, 방 색상·이름, 멤버 수 등 리스트 렌더링에 필요한 메타를 포함한다.
- 방 카드 썸네일(`thumbnailList`): 최근 저장된 핀 최대 4개의 장소 대표 이미지 URL(최신순, 대표 이미지 없는 핀은 제외). **저장된 핀이 0개인 방은 방 대표 색상 키 1개로 폴백**한다(핀은 있지만 이미지가 전부 없으면 빈 목록) — 클라이언트는 색+캐릭터 기본 썸네일로 렌더링(기획 확정).
- 나간 방은 제외한다(`room_members.deleted_at`이 방을 나간 시점이므로 살아있는 멤버십만 조회).
- CTA·생성 유도 바텀시트 노출 조건에 쓸 수 있도록 **공동방 생성/보유 이력**을 판별 가능해야 한다.

### [004] 방 상세

> **목록 정렬 5종은 확정, 뷰 전환은 미결이다.** 정렬 정의는 아래 표를 따르고, **카드형/리스트형 뷰 전환**은 아직 확정되지 않았다. (→ [미결 1](#7-미결-사항-open-questions))

#### 목록 정렬 (5종)

지도 상단 드롭다운. **기본값은 `전체`**이며, [003] 방 리스트와 [004] 방 상세가 같은 정의를 쓴다.

| 항목 | 조건 |
|---|---|
| `전체` (기본) | 필터 없음 |
| `꾹 Pick` | 저장일(`pins.created_at`) 오래된 순 **상위 30%** |
| `최신순` | 저장일 최신순 |
| `거리순` | 요청 좌표 기준 **반경 3km 이내** |
| `코멘트순` | 코멘트 수 **상위 30%** |

- **`꾹 Pick`의 판정 기준이 [[002] 홈 탭](#002-홈-탭-카드-덱-탐색)과 다르다.** 홈은 묵힘(`coalesce(마지막으로 열어본 시점, 저장일)`) 오래된 순이고 상위 30% 제한이 없는 반면, 이 목록은 저장일 기준 상위 30%다. 같은 이름이 두 정의를 가리키므로 통일 여부를 확인해야 한다.
- **장소분류 라벨 4종은 여기에 없다.** 라벨은 홈 카드 덱에만 붙는 표시이고, 이 목록은 정렬만 한다.

방에 저장된 핀 목록과 방 단위 액션. 바텀시트 3단(peek / half / full).

- **핀 리스트**: 방의 핀들을 리스트로 확인
- **다른 방에 공유**: 핀을 다른 방으로 복제, 완료 시 토스트 피드백
  - 대상 방 목록에서 **이미 같은 장소가 저장된 방은 선택됨/비활성 상태로 표현**한다. 사용자가 해제 가능한 것처럼 보이지 않도록 처리한다. (디자인 리뷰 확정 — 서버가 판별 가능함을 개발에서 확인)
- **친구 초대**: 초대 링크 공유
- **방 편집**: 이름·색상 변경
- **방 나가기**: 모든 참여자가 가능하다.
- **방장 위임**: 방장이 나갈 때는 **위임 대상 선택 모달**을 제공한다. 자동 위임 대신 누구에게 넘어가는지 명시적으로 보여준다. (디자인 리뷰 확정)
- ~~**링크로 장소 직접 추가**~~ — 스펙 아웃 (→ [2장 비목표](#비목표-mvp에서-다루지-않음))

**권한 정책** (디자인 리뷰 확정)

| 동작 | 방장 | 일반 참여자 |
|---|---|---|
| 방 생성 | ✅ | ✅ (생성자가 그 방의 방장이 됨) |
| 방 정보 편집(이름·색상) | ✅ | ❌ |
| 방 나가기 | ✅ (위임 필요, 마지막 멤버면 위임 없이 가능) | ✅ |
| 방장 위임 | ✅ | ❌ |
| 방 삭제 | ❌ 명시적 기능 없음 — 단, **방장이 마지막 멤버로 나가면 방이 삭제(soft delete)됨** (PR 리뷰 확정) | ❌ |

**백엔드 관점**

- 방 상세 = 방 정보 + 핀 리스트(지도뷰용 좌표 포함). 요청 유저의 멤버십을 검증한다.
- **지도에 표시하는 핀은 페이지네이션 없이 전체 반환한다. 성능 저하가 확인되면 리팩토링한다.** (PR 리뷰 확정)
- 방장 판별은 `rooms.owner_id`로 한다. 스키마에 이미 존재하며, 주석에도 "방장 탈퇴 시 위임은 애플리케이션에서 처리한다"고 명시되어 있다.
- 방 나가기 = `room_members.deleted_at` 기록(soft delete). 살아있는 행끼리만 유니크하므로 나갔던 방에 다시 합류할 수 있다.
- **방장 위임은 별도 API로 처리하고, 나가기는 위임 완료 후에만 허용한다.** 나가기 요청 시 서버가 방장 여부를 검증해, 방장이 다른 멤버를 남겨둔 채 요청하면 에러로 분기한다(위임 유도).
- **방장이 마지막 멤버인 경우 위임 없이 나가기를 허용하고, 방을 삭제(soft delete) 처리한다.** (PR 리뷰 확정 — 구 미결 7 해소)
- 개인방(`type: personal`)은 나가기·위임·편집 대상이 아니며, **초대·합류 대상도 아니다.** 개인방의 초대 코드로 들어오는 합류 요청은 거절한다. (PR 리뷰 확정)
- 다른 방 공유 대상 목록을 줄 때 **각 방에 해당 장소가 이미 저장되어 있는지**를 함께 반환한다. `pins`를 `place_id`로 조회해 판별 가능하다.
- 핀 복제 시 원본 방·대상 방 **양쪽 멤버십**을 검증한다.

### [005] 장소 상세 (+ 지도뷰)

- **지도뷰**: 방의 핀들을 지도 위에 표시
- **카테고리 필터는 `전체`·`카페`·`음식점` 3종 고정**이며 기본값은 `전체`다. 저장 값 기반 동적 생성은 하지 않는다. 버튼은 바텀시트 내부가 아니라 **지도 상단에 배치**한다. (디자인 리뷰 확정 — 바텀시트가 담는 정보가 과했음)
- **장소 상세**: 장소 정보(이름·주소·카테고리 등) + 출처 링크 + 코멘트 (half / full)
- **코멘트**: 방 멤버가 핀에 코멘트 작성 (empty state: "아직 코멘트가 없어요!")
- **다른 방에 공유**: 장소 상세에서 바로 다른 방으로 공유한다. (~~새 방 만들기~~ 플로우는 새 보드에서 제거됨)
- **외부 지도 앱 이동 버튼**: 기존 라이팅이 실제 경로 탐색 기능처럼 오해될 수 있어 **라이팅 수정이 우선**이다. 카카오맵만 가능한 제약이 있어 아이콘 중심 표현은 애매하고, 복잡한 선택 모달은 현 단계에서 과하다. (디자인 리뷰 확정)
- **X 버튼은 장소 상세에만 둔다.** 그 외 바텀시트의 X 버튼은 전부 제거한다. (PR 리뷰 확정 — 구 미결 3 해소)

**백엔드 관점**

- 지도뷰는 [004] 방 상세의 핀 리스트를 좌표와 함께 재사용한다. 별도 엔드포인트를 두지 않는다.
- 카테고리 필터는 `places.category` 기준이다. 지오코더(Kakao/Google) 응답 체계가 provider마다 달라, 원본 카테고리를 **`cafe` / `restaurant` / 그 외** 3분류로 접는 매핑 규칙이 필요하다. 어디에도 안 걸리는 값은 `전체`에서만 보인다.
- **장소분류 라벨(`labelGroup`)은 이 화면에서 판정하지 않는다.** 홈 카드 덱이 부여한 값을 클라가 들고 와 표시하므로, `GET /pins/{pinId}` 응답에는 포함되지 않는다.
- 장소 상세 = 장소 정보 + 출처 링크(`place_sources` → `sources.original_url`) + 코멘트 목록/수.
- 코멘트 작성·조회·삭제 모두 방 멤버십을 검증한다. **삭제는 작성자 본인만 가능하다.** (PR 리뷰 확정) 삭제는 soft delete(`pin_comments.deleted_at`)로 처리한다. **수정은 MVP 미지원**(삭제 후 재작성)이며 수정 API를 두지 않는다.
- 코멘트 목록 정렬은 **`createdAt` 오름차순(ASC)** — 최신 코멘트가 목록 맨 아래에 온다.
- 외부 지도 앱 이동은 클라이언트가 좌표·장소명으로 딥링크를 구성한다. 서버 작업 없음.

### 친구 초대 · 방 합류 ([001]·[004] 하위 플로우)

> **TBD — 초대 관련 UI/플로우 기획은 변경 여지가 있다.** 아래 확정 항목 외의 화면 구성은 확정 스펙으로 다루지 않는다.

- 초대 링크(`gguk.org/r/{code}`) 생성·공유
- 링크로 진입한 사용자는 **프로필 설정 후 초대를 수락**해 방 멤버가 된다. (PR 리뷰 확정)
- **초대 링크 유효기간은 무제한**이고, **거절 개념은 없다.** (PR 리뷰 확정)
- **합류 완료 시 방 멤버 전원에게 푸시 알림을 발송한다.** (PR 리뷰 확정)
- 중복 참여는 불가 (`room_members (room_id, user_id)` 살아있는 행 유니크)
- 초대 화면에서 **"친구 초대하기"(시스템 공유 시트)와 "초대 링크 복사"** 는 같은 링크를 쓴다.
- 초대받은 화면은 **"OO님이 공동방에 초대했어요"** 로 초대자를 보여주고, 방 이름·설명·색상·멤버 아바타·장소 수를 함께 노출한다.

**백엔드 관점**

- 초대 코드로 방을 미리보기하는 조회는 **인증 없이** 가능해야 한다(앱 설치 전/온보딩 전 진입). 응답은 **`room`(id·type·이름·설명·색상·핀 수·멤버 수·멤버 아바타 최대 5)과 `inviter`(닉네임·아바타)** 로 엔티티 단위로 묶는다. 클라이언트가 Room/User 타입을 그대로 재사용할 수 있고 자원의 소속이 드러난다. 합류 API가 path로 방을 요구하므로 `room.id`가 초대받은 사람의 유일한 획득 경로다. (PR 리뷰 확정)
- 형식이 어긋난 코드는 DB를 조회하기 전에 거절한다.
- 초대는 **`invitations` 테이블**(방 참조 + 초대자 참조 `invited_by`)로 관리한다. `(room_id, invited_by)` 유니크라 **초대는 멤버당 1개**다. 링크를 공유한 멤버가 그대로 초대자로 표시되며, 방당 1개로 두면 초대자가 최초 생성자로 고정돼 화면과 어긋난다.
- **개인방은 초대 불가다.** 개인방 초대 코드로의 미리보기/합류 요청은 거절한다. 개인방에는 초대를 발급하지 않으므로 링크 자체가 생기지 않는다. (PR 리뷰 확정)
- 합류는 인증 후 처리하며, 이미 멤버면 오류 대신 멱등 응답을 준다. `inviteCode`가 가리키는 방이 요청 경로의 방과 다르면 거절한다.
- 나갔던 방에 같은 초대 코드로 재합류하면 새 `room_members` 행이 생긴다(이전 행은 `deleted_at` 유지).
- 초대 코드는 `invitations.code`에 보관하며 **대문자 영문 + 숫자 6자 고정**이다. 경우의 수가 36^6 ≈ 21.8억이라 발급 시 유니크 충돌이 나면 새 코드로 재시도한다.
- 발급은 멱등하다. 이미 있으면 같은 코드를 돌려주고 재발급하지 않는다. **수명주기는 없다 — 만료·재발급을 두지 않는다.** (PR 리뷰 확정)
- 링크 조립(`gguk.org/r/{code}`)은 클라이언트가 한다. 서버는 코드만 반환하고 도메인을 알지 않는다.

### [006] 알림함

알림함 스펙(내부 문서, notifications 3.0.0)에서 화면 구성과 알림 유형이 확정됐다. 화면 단위 상세는 스펙 문서를 따르고, 이 절은 PRD 수준에서 필요한 부분만 옮긴다.

**확정분 (알림함 스펙 3.0.0 기준)**

알림 유형은 다음 6종으로 고정된다.

| 유형 | 문구 | 대상 | 발송 시점 |
|---|---|---|---|
| 중복 저장 | 이미 저장해둔 곳이에요 | 장소명 | 링크 분석 중 저장 시도가 중복으로 판정될 때 |
| 저장 오류 | 장소를 저장하지 못했어요. | 고정 안내 3줄 | 링크 분석이 최종 실패할 때 |
| 위치 기반 리마인드 | 근처에 저장한 장소가 있어요 | 장소명 | 저장은 했지만 아직 방문하지 않은 장소 근처에 진입했을 때 |
| 코멘트 기반 리마인드 | 코멘트가 제일 많이 달린 장소에요 | 장소명 | 저장 핀 중 코멘트가 가장 많은 장소를 주기적으로 안내할 때 |
| 공동방 참가(기존 멤버) | {참가자 이름}님이 들어왔어요 | 공동방 이름 | 초대 코드로 다른 사람이 방에 합류했을 때 |
| 공동방 참가(본인) | 방에 참가했어요 | 공동방 이름 | 본인이 초대 코드로 방에 합류했을 때 |

- 알림함은 읽음/안읽음 상태를 두지 않는다. 목록은 발생한 사실을 훑어보는 기록이고, 안 읽은 개수 배지도 없다.
- 알림 목록은 기본 20건 페이지네이션이며 기간, 총량 상한이 없다.
- 장소 대상 알림 payload는 `placeId`와 `pinId`를 모두 포함한다. 모바일은 `pinId`로 알림이 발생한 핀의 장소 상세를 열고, 해당 핀이 삭제됐거나 접근할 수 없으면 `placeId`를 폴백 식별자로 사용한다.
- 한 번의 저장 시도에서 여러 방이 동시에 중복이어도 알림은 장소당 한 건으로 묶는다.

위치 기반 리마인드의 트리거 방식(클라이언트 지오펜스 또는 서버 위치 폴링)은 백엔드 설계 단계에서 정한다. 코멘트 기반 리마인드의 발송 주기는 확정을 기다리지 않고 임시값으로 운영하며 이후 조정한다.

**미결**

- "N명이 저장했어요" 형태의 푸시 알림이 논의된 적 있으나 알림함 스펙 3.0.0의 6종에는 없다. 홈 카드 라벨 "여럿이 저장한 곳"(중복 저장 수)과 혼동됐을 가능성이 있어, 문구와 발송 기준을 디자인팀에 확인해야 한다.

**백엔드 관점**

- 알림 레코드 테이블이 필요하다: 수신자, 유형, 참조 대상(장소 알림은 `placeId`와 `pinId`, 방 알림은 `roomId`), 참가자(공동방 참가 유형에서만), 생성 시각. 읽음 시각 컬럼은 두지 않는다.
- 같은 사건이 재전달, 재실행으로 중복 기록되지 않도록 dedup 키가 필요하다(저장 시도 단위 또는 유저와 장소 조합 단위).
- 푸시 발송을 위해 사용자별 디바이스 푸시 토큰 저장이 필요하다(FCM). 재설치로 새 유저가 생성됐을 때 이전 유저 행에 남은 토큰을 회수하는 처리를 포함한다.

### [007] 마이페이지

새 보드에서 범위가 확정됐다: **다크모드(테마) / 알림 설정 / 위치 설정 / 약관 동의 / 앱 리뷰**(App Store 꾹 페이지로 이동). 닉네임·프로필 수정도 마이페이지에서 진입한다.

**백엔드 관점**

- 닉네임·프로필 이미지 수정은 [001]에서 만든 프로필 API를 재사용한다. 공통 프로필이므로 모든 방에 즉시 반영된다.
- 테마(다크모드)는 클라이언트 로컬 설정으로 두면 서버 작업이 없다.
- **알림 설정(수신 on/off)** 은 서버 발송 필터로 쓰려면 사용자 설정 저장이 필요하다 — 알림 기획(TBD) 확정 시 함께 정한다.
- 위치 설정은 OS 권한 설정 연결로, 서버 작업 없음.
- 약관은 정적 문서 링크로 처리한다. 버전 관리·동의 이력이 필요하면 별도 설계가 필요하다.
- 계정 탈퇴는 MVP 비목표다. (스키마에는 `users.deleted_at`과 활성 행 부분 유니크가 이미 있어 나중에 붙일 수 있다)

## 5. 데이터 모델 개요

PR #44에서 8개 테이블이 정의·머지됐다. **모든 테이블에 soft delete(`deleted_at`)가 적용**되어 있고, 유니크 제약은 살아있는 행에만 걸리는 **부분 유니크 인덱스**로 구현되어 있다(삭제 후 재생성 가능).

| 테이블 | 역할 | 비고 |
|---|---|---|
| `users` | device_id 기반 사용자 | 닉네임(varchar 15)·아바타 객체(`avatar` jsonb, `{color}`+확장 필드). `device_id`는 살아있는 행끼리만 유니크 |
| `rooms` | 방 | `type`: `personal` / `shared`, **`owner_id`(방장)**, 이름(`varchar(20)` — 정책상 최대 15자)·설명(정책 30자)·색상(팔레트 키 `varchar(16)`). 초대 코드는 `invitations`로 분리됐다 |
| `room_members` | 방 멤버십 | `(room_id, user_id)` 활성 유니크. `deleted_at` = **방을 나간 시점** |
| `invitations` | 초대 링크 | 방 참조 + **초대자 참조(`invited_by`)**, `code`(대문자 영문 + 숫자 **6자 고정**, 유니크). `(room_id, invited_by)` 유니크 = **멤버당 초대 1개** |
| `sources` | 출처 링크 | `type`: instagram / naver_map / google_map / manual, `original_url` 활성 유니크, `metadata`(스크랩 원문 jsonb) |
| `places` | 장소 마스터 | `(provider, provider_place_id)` 유니크로 dedup (provider: kakao / google) |
| `place_sources` | 장소↔출처 N:M | `(place_id, source_id)` 활성 유니크로 재유입 시 기존 연결 재사용 |
| `pins` | 방에 저장된 장소 | `(room_id, place_id)` 활성 유니크, `source_id`·`created_by` nullable, `last_accessed_at` |
| `pin_comments` | 핀 코멘트 | 작성자가 방 멤버인지는 애플리케이션 레벨에서 검증. 삭제는 작성자 본인만 |

## 7. 미결 사항 (Open Questions)

확정되지 않아 관련 피쳐 개발 전 결정이 필요한 항목. `TBD`는 기획 변경이 진행 중이라 확정 스펙을 적지 않는 영역이다.

1. **[004] 카드형/리스트형 뷰 전환**: 목록 정렬 5종은 확정됐으나 뷰 토글은 보류. 도입 시 조회 계약이 아니라 클라 표현만 달라지는지 확인 필요.
2. **"다른 방에 공유" UI 형태**: 바텀시트가 최선인지 검토 여지가 있다. 뒤에 맥락 화면이 있으면 바텀시트가 적절하지만, 독립적 선택이 필요한 경우 모달/페이지가 나을 수 있다.
3. **알림함 세부 트리거**: 화면 구성과 6종 알림 유형은 알림함 스펙 3.0.0에서 확정됐다(→ [4장 [006]](#006-알림함)). 남은 것은 위치 기반 리마인드의 트리거 방식(클라이언트 지오펜스 또는 서버 위치 폴링)과 스펙 6종에 없는 "N명이 저장했어요" 유형의 추가 여부다. 코멘트 기반 리마인드의 발송 주기는 임시값으로 운영하며 이후 조정한다(확정 대기 대상 아님).
4. **다중 장소 추출 처리 정책**: 한 게시물에서 장소 N개가 추출될 때 핀 생성·부분 성공·푸시 발송 횟수. 오류 상황 상세 정의 후 프디팀과 확정. (PR 리뷰 결론)
5. **개인방 색상**: ~~프디팀 추후 결정~~ → **해결** — 개인방("내 장소") 기본 색상은 팔레트 키 `gray`(디자인 확정). 클라이언트는 개인방 기본 썸네일을 회색 이미지로 렌더링한다.
6. **닉네임 중복 허용 범위**: 스키마상 닉네임 유니크 제약이 없어 중복 가능하다. 전체 유저 간 허용인지, 방 안에서만 제한할지 프디팀 확인 필요. (PR 리뷰 질문 — 미답)
7. **방 커버 도입 여부**: 새 보드에 "방 커버 변경 예정" 주석이 있다. 도입되면 `rooms`에 커버 필드가 필요할 수 있다.
8. **방 변경 시 라벨 vs 툴팁**: 디자인 리뷰에서는 고정 라벨로 확정했으나 새 보드에 "툴팁 3초 유지" 화면이 남아 있다. 재확인 필요.

## 8. API 설계 초안 (RESTful Draft)

경로·메서드 수준의 초안이다. 요청/응답 스키마, 에러 코드 값, 페이지네이션 상세는 각 피쳐 PR에서 확정한다.

**공통 규칙**

- 베이스 경로: `/api/v1` (기존 `PlaceController` 컨벤션 유지)
- 인증: **별도 인증 설계에서 확정한다**(잠정: `Authorization: Bearer <token>`). 인증 예외 엔드포인트는 등록(`POST /users`)과 초대 미리보기(`GET /invitations/{code}`)뿐이다.
- **에러 응답은 기존 공통 예외 필터의 `errorCode` 포맷을 따른다.** (PR 리뷰 확정)
- 목록 API 페이지네이션은 **offset 기반으로 통일한다**: `page`(0부터 시작)·`pageSize` 쿼리 파라미터, 응답에 `pagination { pageSize, page, hasNext }` 객체 포함. 단, **지도용 핀 전체 조회는 페이지네이션 없이 전체 반환한다**(성능 저하 확인 시 리팩토링, PR 리뷰 확정).
- 리소스는 복수형 명사, 동작은 HTTP 메서드로 표현한다. 상태 변경 기록처럼 명사화가 자연스러운 동작은 하위 컬렉션(`/accesses`)으로 표현한다.
- 부분 수정은 `PATCH`, 컬렉션 추가는 `POST`
- 방 스코프 리소스는 전부 요청 유저의 멤버십을 검증한다.

**세부 계약 메모**

- `GET /rooms`: `?showHasPlaceId={placeId}`를 주면 각 방에 해당 장소가 이미 저장되어 있는지(`hasPlace`)와 매칭되는 활성 핀 ID(`matchedPinId`)를 함께 반환한다. "다른 방에 공유" 화면에서 이미 저장된 방을 선택됨/비활성으로 그리는 데 쓴다.
  - `matchedPinId` 진리표(truth table):
    - `showHasPlaceId` 쿼리 생략: `hasPlace`, `matchedPinId` 속성 자체를 미포함 (omitted)
    - 쿼리 제공 + 활성 매칭 핀 존재: `hasPlace: true`, `matchedPinId: string` (해당 활성 핀 UUID)
    - 쿼리 제공 + 매칭 핀 없음: `hasPlace: false`, `matchedPinId: null`
    - 쿼리 제공 + soft delete된 핀만 존재: `hasPlace: false`, `matchedPinId: null`
    - 쿼리 제공 + 삭제된 과거 핀과 활성 교체 핀 공존: `hasPlace: true`, `matchedPinId: string` (활성 교체 핀 UUID만 반환)
- `DELETE /rooms/{roomId}/members/me`: 파라미터 없이 요청하고 **서버가 요청 유저 상태를 검증해 분기한다.** 일반 멤버는 나가기 처리, **방장 + 다른 멤버 존재면 에러로 거절**(먼저 `PUT /rooms/{roomId}/owner`로 위임, errorCode 예: `OWNER_TRANSFER_REQUIRED`), **방장 + 마지막 멤버면 나가기 허용 + 방 soft delete.** (PR 리뷰 확정) 개인방은 나가기 대상이 아니다.
- **명시적 방 삭제 엔드포인트는 두지 않는다.** 방 삭제는 마지막 멤버 나가기 시 서버가 처리하는 결과다.

### 초대 / 멤버십

| Method | Path | 설명 | 화면 |
|---|---|---|---|
| `POST` | `/api/v1/rooms/{roomId}/invitations` | **내 초대 링크 발급** (멤버당 1개, 이미 있으면 같은 코드 — 멱등) | 초대 |
| `GET` | `/api/v1/invitations/{code}` | 초대 코드로 방 미리보기 (**인증 불필요**) — 노출: `room`(이름·설명·색상·핀 수·멤버 수·아바타)과 **`inviter`** | 초대 |

| `GET` | `/api/v1/rooms/{roomId}/members` | 방 멤버 목록 (방장 위임 대상 선택 모달용) | [004] |

> `POST /rooms/{roomId}/members`는 "멤버 컬렉션에 나를 추가"로 읽힌다. `/join` 같은 동사 경로를 쓰지 않는 이유이며, 나가기(`DELETE .../members/me`)와도 대칭을 이룬다.

**세부 계약 메모**

- `POST /rooms/{roomId}/invitations`: 요청 유저의 멤버십을 검증하고 그 유저 이름으로 초대를 발급한다. `(room_id, invited_by)` 유니크라 재요청 시 같은 코드가 돌아온다. 응답은 `code`뿐이고 링크 조립은 클라이언트가 한다. 생성이 아니라 get-or-create라 `201`이 아닌 `200`을 반환한다.
- `GET /invitations/{code}`: 응답을 `room`과 `inviter` 엔티티 단위로 묶는다. `room.id`는 초대받은 사람이 합류 API의 path `roomId`를 얻는 유일한 경로다. (PR 리뷰 확정) 인증 없이 열리므로 멤버 아바타는 최대 5명까지만 내려준다.
- `POST /rooms/{roomId}/members`: body의 `inviteCode`로 `invitations`에서 활성 초대를 찾고 **그 초대의 방이 path의 `{roomId}`와 같은지 검증**한다. 불일치하거나 무효한 코드는 멤버 추가 전에 거절한다. **개인방의 코드는 거절한다.** (PR 리뷰 확정) 멱등이라 `201`이 아닌 `200`을 반환한다.
- 합류 완료 시 방 멤버 전원에게 푸시 알림을 발송한다. (PR 리뷰 확정)
- 초대 리소스 분리(`invitations`: 방·초대자 참조)는 완료됐다.

**세부 계약 메모**

- `POST /rooms/pins`: body는 `{ url, roomIds }`이며 `roomIds`는 비어 있지 않은 중복 없는 배열이다. **enqueue 전에 모든 `roomIds`에 대한 요청 유저의 멤버십을 검증한다.** 하나라도 유효하지 않으면 source를 등록하거나 작업을 생성하지 않고 거절한다. 서버는 `sources` 등록과 enqueue까지만 동기로 하고 즉시 `202`를 반환한다. 스크랩·LLM·지오코딩 지연 때문에 동기 응답이 불가하다는 것이 회의 결론이다.
  - Cloud Tasks 작업 하나가 URL을 한 번 스크랩·추출·지오코딩하고, 성공 장소를 모든 선택 방에 저장한다. 작업 대기 중 사용자가 특정 방을 나갔으면 그 방만 제외하며, 모든 대상이 무효면 작업을 acknowledge한다.
  - 기존 `POST /api/v1/place/places`(`src/modules/place/place.controller.ts`)가 동기 추출을 하고 있어, 이 경로로 정리하며 흡수한다.
  - MVP 지원 출처는 인스타그램 링크뿐이다. 그 외 URL은 명시적으로 거절한다.
  - 한 게시물에서 장소 N개가 추출되는 경우의 처리(핀 N개·부분 성공·푸시 횟수)는 미결 4 확정 후 계약에 반영한다.
- 별도 상태 조회 API를 두지 않는다. 처리 결과는 푸시(중복·실패)와 알림함으로만 전달한다. 앱이 포그라운드일 때 성공 케이스의 안내 방식은 미결이다(7장 미결 참조).
- `POST /rooms/pins`: **링크 분석 접수 전용**이다. "다른 방에 공유(복제)"는 `POST /pins/{pinId}/duplicate`를 사용한다.
  - `POST /pins/{pinId}/duplicate`: 원본 핀의 장소를 **여러 대상 방에 복제**한다(신규 저장 경로가 아니라 링크 분석 워커가 신규 저장을 처리). 원본 방·모든 대상 방 멤버십을 검증하고, **대상 방 중 하나라도 같은 장소가 이미 저장돼 있으면 409로 전체 거절**한다. (swagger 확정)
- `GET /rooms/{roomId}/cards`: `sort`로 후보 10장을 뽑고 각 카드에 `labelGroup`을 붙인다. 라벨 판정은 서버가 한다. 자격 미달로 남은 자리는 `가볼 만한 곳`이 흡수하므로 후보가 10장이면 덱도 10장이다. **페이지네이션도 재생성 계약도 두지 않고**, 다시 부르는 시점은 클라이언트가 정한다.
- `POST /pins/{pinId}/accesses`: 개인별 큐레이션이 확정됐으므로 요청 유저 기준으로 접근 행을 남긴다. `pins.last_accessed_at` 갱신만으로는 부족하다. "친구들이 많이 본 곳"(클릭수) 집계의 원천 데이터를 겸한다.

### 코멘트

| Method | Path | 설명 | 화면 |
|---|---|---|---|
| `GET` | `/api/v1/pins/{pinId}/comments` | 코멘트 목록 조회 | [005] |
| `POST` | `/api/v1/pins/{pinId}/comments` | 코멘트 작성 | [005] |
| `DELETE` | `/api/v1/pins/{pinId}/comments/{commentId}` | 코멘트 삭제 (soft delete) — **작성자 본인만** (PR 리뷰 확정) | [005] |

코멘트는 `Pin`에 속한다. 개인방·공동방 모두 활성 멤버만 조회·작성·삭제할 수 있다. 방을 나간 작성자의 기존 코멘트는 유지하고, 현재 유저 프로필(닉네임·nullable 아바타)을 표시한다.

- 작성 본문은 앞뒤 공백을 제거한 뒤 1~200자여야 한다. 줄바꿈·이모지·특수문자를 허용하고 동일 본문의 중복 작성도 허용한다.
- 목록은 offset 기반이다. `page=0`, `pageSize=20`(최대 100)이며, 0번 페이지는 최신 묶음이되 배열 안은 오래된 순이다. 다음 페이지는 더 오래된 묶음이고 범위를 넘으면 빈 목록과 `200`을 반환한다.
- 응답 코멘트는 `id`, `content`, UTC ISO 8601 `createdAt`, `author { id, nickname, avatar }`, `canDelete`만 반환한다. 삭제된 코멘트는 목록과 코멘트 수에서 제외한다.
- 삭제 성공 응답은 `200 { data: { ok: true } }`다. 존재하지 않음·이미 삭제됨·다른 핀 소속은 `404 COMMENT_NOT_FOUND`, 다른 작성자의 삭제는 `403 COMMENT_DELETE_FORBIDDEN`이다. 삭제된 핀 또는 방은 `404 PIN_NOT_FOUND`다.

> 코멘트 **수정(`PATCH`)은 MVP 미지원**이다. 잘못 쓴 코멘트는 삭제 후 재작성한다. 지원하게 되면 작성자 본인 + 방 멤버십 검증을 포함해 추가한다.

알림함 스펙 3.0.0에서 6종 알림 유형과 화면 동작이 확정됐다. 남은 미결은 [미결 3](#7-미결-사항-open-questions)를 참고한다.

| Method | Path | 설명 | 화면 |
|---|---|---|---|
| `GET` | `/api/v1/notifications` | 알림 목록 (페이지네이션, 읽음 상태 없음) | [006] |
| `POST` | `/api/v1/notifications/nearby-triggers` | 위치 기반 리마인드 트리거 (클라이언트가 지오펜스 진입을 보고) | [006] |

> 알림 목록의 각 항목은 typeLabel, 대상 이름, 썸네일, 발생 시각, url(딥링크)로 구성한다(4장 [006] 참고). 스킴과 경로 구조는 모바일과 별도로 협의한다.
>
> 코멘트 기반 리마인드는 서버 스케줄러가 주기적으로 판정해 발송한다. 발송용 내부 엔드포인트는 Cloud Tasks 워커와 같은 방식으로 비공개라 이 표에 포함하지 않는다.
>
> Draft OpenAPI Specification은 위 경로가 팀 리뷰로 확정된 뒤, 각 피쳐 PR의 NestJS Swagger 데코레이터로 생성해 누적하는 방식을 제안한다. 스펙 문서를 수기로 선작성하면 구현과 이중 관리가 되기 때문이다. (`@nestjs/swagger`는 이미 의존성에 있다)
