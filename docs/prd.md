## 1. 서비스 개요

**쏙핀은 SNS·지도 앱에서 발견한 장소 링크를 방(Room)에 모아두고, 친구들과 함께 다음 약속 장소를 고르는 서비스다.**

> "카톡방에 흘러간 링크, 그만 찾아 헤매세요. 방에 모아두면 약속 잡을 때 바로 꺼내 써요."
> "'여기 어때?'는 이제 그만. 친구가 들어오면 저장한 장소가 한눈에 모여요. 다음 약속 장소, 여기서 같이 골라요."

### 해결하는 문제

- 인스타그램 등에서 발견한 가고 싶은 장소가 카톡방·북마크에 흩어져 있어, 약속을 잡을 때 다시 찾기 어렵다.
- 장소 링크(게시물)에는 구조화된 장소 정보(이름·주소·좌표)가 없어, 지도에서 다시 검색하는 수고가 필요하다.
- 모임 단위로 장소 후보를 모으고 의견을 나눌 공간이 없다.

### 핵심 컨셉

- **공유 시트로 유입**: 인스타그램에서 시스템 공유 시트를 통해 링크를 쏙핀으로 보내면, 장소가 자동으로 추출되어 방에 핀으로 저장된다. 추출에는 시간이 걸리므로 **접수는 즉시 응답하고 결과는 푸시 알림으로 안내한다.** (디자인 리뷰 확정 → [4장 [000]](#000-공유-유입))
- **방(Room) 중심 구조**: 모든 핀은 방에 속한다. 온보딩 시 생성되는 개인방("내 방")과, 초대 코드로 친구를 모으는 공동방이 있다.
- **카드 탐색**: 홈에서 방의 핀을 카드 덱으로 탐색하고("꾹 눌러둔 장소, 다시 꺼내볼까요?"), 지도·리스트로도 확인한다. 카드 소비 상태는 **개인별**이라 다른 멤버에게 영향을 주지 않는다. (디자인 리뷰 확정)
- **공통 프로필 1회 설정**: 닉네임·프로필 이미지는 최초 진입 시 1회만 받고 모든 방에 공통 적용한다. 방별 닉네임/프로필 분리는 하지 않는다. (디자인 리뷰 확정)
- **로그인 없는 MVP**: 계정 가입 없이 `device_id`로 최초 1회 등록하고, 이후 요청은 서버 발급 토큰으로 인증한다. (→ [2.1 인증·보안 모델](#21-인증보안-모델-mvp))

## 2. 목표 / 비목표

### 목표 (MVP 범위)

- 링크 공유 → 장소 추출 → 핀 저장의 핵심 루프가 **인스타그램 링크** 기준으로 동작한다.
- 처리 결과(성공 / 중복 저장 / 오류)를 **푸시 알림 + 알림함**으로 안내한다.
- 개인방·공동방을 만들고, 초대 링크(e.g, `ssokpin.org/r/{code}`)로 친구가 합류할 수 있다.
- 방의 핀을 홈 카드 덱 / 지도 뷰 / 리스트로 탐색하고, 장소 상세에서 코멘트를 나눌 수 있다.
- 핀을 다른 방으로 공유(복제)할 수 있다.
- **방 나가기**와 **방장 위임**이 가능하다.
- 마이페이지에서 약관 확인·테마 변경·닉네임/프로필 수정이 가능하다.

### 비목표 (MVP에서 다루지 않음)

- 소셜 로그인·계정 시스템 (device_id 등록 + 서버 발급 토큰으로 대체)
- **인스타그램 외 출처**(네이버지도 / 구글맵 / 수동 입력) — MVP 1단계 미반영 (디자인 리뷰 확정)
- **장소 직접 추가** — 구현 비용 대비 사용자 가치가 낮아 스펙 아웃. 유입은 인스타그램 공유 시트로 일원화한다. (디자인 리뷰 확정)
- **방 삭제** — 방을 폭파시키는 개념 대신 `방 나가기 + 방장 위임` 구조로 간다. (디자인 리뷰 확정)
- **계정 탈퇴** — 디바이스 중심 구조라 우선순위가 낮다. (디자인 리뷰 확정)
- 방별 닉네임/프로필 분리

> 참고: 푸시 알림은 이전 버전에서 비목표였으나, 링크 처리 지연 때문에 **결과 전달의 유일한 수단**이 되어 목표로 승격됐다. (디자인 리뷰 확정)

### 2.1 인증·보안 모델 (MVP)

로그인이 없으므로, 무엇을 보호하고 무엇을 감수하는지를 명시해 둔다.

**보호 대상 자산**

- 방 정보와 멤버 목록, 방에 저장된 핀·장소
- 프로필(닉네임·프로필 이미지)
- 핀 코멘트, 알림함 내역

**인증 방식**

- 등록(`POST /users`)은 **create-only**다. 이미 등록된 `device_id`로 다시 등록을 요청하면 토큰을 재발급하지 않고 `409 Conflict`로 거절한다.
  - `device_id`를 upsert 키로 쓰면 안 된다. 등록 엔드포인트는 인증 예외인데, `device_id`는 클라이언트가 임의 값으로 제출할 수 있으므로 **타인의 `device_id`를 제출해 그 사용자의 토큰을 받아가는 계정 탈취**가 성립한다.
- `device_id`는 클라이언트가 **최초 1회 생성하는 128비트 이상 난수**이며, iOS Keychain / Android Keystore 등 보안 저장소에 보관한다.
  - IDFV·`ANDROID_ID`처럼 추측·수집 가능한 시스템 식별자를 그대로 쓰지 않는다. 등록이 create-only여도, 선점되지 않은 `device_id`를 추측할 수 있으면 타인 명의 선등록이 가능하다.
- 등록 응답으로 **서버가 발급한 불투명(opaque) 토큰**을 내려주고, 이후 모든 요청은 `Authorization: Bearer <token>`으로 인증한다. 서버는 **토큰으로만** 요청 유저를 결정하며, 요청 본문/헤더의 `device_id`는 신원 증명으로 쓰지 않는다.
- 인증 예외는 등록(`POST /users`)과 초대 미리보기(`GET /invitations/{code}`) 둘뿐이다.
- 방 스코프 리소스(핀·코멘트·멤버·알림)는 요청 유저의 `room_members` 소속 여부를 검증한 뒤 처리한다.

**MVP에서 감수하는 위험 (allowed risk)**

- 토큰이 유출되면 해당 유저로 위장 가능하다. 토큰 회전·폐기·다중 기기 세션 관리는 MVP 비목표이며, 계정 시스템 도입 시 다룬다.
- 앱 삭제·재설치 또는 기기 변경으로 `device_id`와 토큰을 모두 잃으면 기존 유저로 복구할 수 없다. 새 `device_id`로 새 유저가 되며, 이전에 속한 방은 초대 링크로 다시 합류해야 한다. (복구 수단 = 계정 시스템, MVP 비목표)
- 초대 링크를 입수한 사람은 누구나 방에 합류할 수 있다. 링크 자체가 방의 접근 권한이다.
- 저장되는 데이터에 민감정보(연락처·결제·위치 이력)를 포함하지 않는 것을 전제로 한다.

## 3. 핵심 사용자 시나리오

디자인은 두 가지 진입 케이스를 구분한다.

### Case 1: 최초 초대자 (방을 만드는 사람)

1. 스플래시에서 위치·알림 권한 요청 (디자인 리뷰 확정 — 초반 진입 구간에서 단순하게 요청)
2. 온보딩·튜토리얼: 프로필 설정(닉네임 + 프로필 이미지) → 공동방 만들기(이름·색상) → 친구 초대 → SNS 공유 연습 → 완료
3. 인스타그램에서 마음에 드는 장소 게시물을 발견 → 공유 시트에서 쏙핀 선택 → 저장할 방 선택 → **접수 피드백** → 처리 완료 후 **푸시 알림**
4. 홈에서 카드 덱으로 저장된 장소를 탐색, 지도/리스트에서 확인
5. 친구들과 장소 상세에서 코멘트로 의견 교환

### Case 2: 초대받은 사람

1. 초대 링크(`ssokpin.org/r/{code}`)로 진입 → 프로필 설정 → 방 합류
2. 이후 흐름은 Case 1과 동일 (링크 저장, 탐색, 코멘트)

> 초대 수락과 닉네임 설정의 **순서는 미결**이다. 초대 맥락을 먼저 보여주자는 의견과, 공통 프로필 1회 설정이니 진입 시 먼저 받자는 의견이 갈렸다. 전체 플로우 정리 후 판단한다. (→ [미결 2](#7-미결-사항-open-questions))
>
> 온보딩 "건너뛰기" 시 도달 지점, 인스타그램 → 앱 유입 과정, 초대 링크 → 설치 → 진입 → 수락 순서는 **화면 단위 디자인과 별개로 전체 플로우 문서가 필요**하다는 것이 회의 결론이다. 확정되면 이 장을 갱신한다.

## 4. 기능 정의

Figma 섹션 번호([000]~[006])를 기준으로 하고, 회의에서 신규로 정해진 화면은 `[신규]`로 표기한다.
각 절의 **백엔드 관점**은 해당 화면이 서버에 요구하는 동작을 정리한 것으로, [8장 API 초안](#8-api-설계-초안-restful-draft)·[9장 태스크](#9-기능별-태스크-리스트)와 대응된다.

### [000] 공유 유입

인스타그램에서 시스템 공유 시트로 링크를 쏙핀에 공유하는 핵심(이자 유일한) 유입 경로.

- 공유 버튼 클릭 → 공유 대상(쏙핀) 선택 → 저장할 방 선택 → **접수 피드백**
- 스크랩 → LLM 장소 추출 → 지오코딩에 시간이 걸리므로, **응답 완료까지 기다렸다가 토스트를 띄우는 방식은 쓰지 않는다.** 즉시 가능한 범위(접수됨)까지만 피드백하고, 실제 결과는 푸시 알림으로 안내한다. (디자인 리뷰 확정)
- 결과 유형: **성공 / 중복 저장 / 오류** — 모두 푸시 알림 + 알림함으로 관리한다.

**백엔드 관점**

1. 링크 접수: `original_url` 정규화 → `sources` 조회·등록(살아있는 행 기준 유니크이므로 재유입 시 기존 행 재사용) → 분석 잡 생성 후 **즉시 202 응답**(`jobId` 반환).
2. 백그라운드 처리(Cloud Tasks 워커): 스크래핑(`infrastructures/scraper`) → AI 장소 추출(`infrastructures/ai`) → 지오코딩(`infrastructures/geocoder`, Kakao/Google).
3. 저장: `places`에 `(provider, provider_place_id)` 기준 dedup upsert → `place_sources` 연결(`(place_id, source_id)` 살아있는 행 유니크라 재유입 시 기존 연결 재사용) → 선택한 방에 `pins` 생성.
4. 중복 판정: 같은 방에 같은 장소가 이미 있으면(`pins (room_id, place_id)` 살아있는 행 유니크) 새 핀을 만들지 않고 **중복 결과**로 처리한다.
5. 결과 알림: 잡 종료 시 결과 유형별 알림 레코드를 남기고 푸시를 발송한다. 중복인 경우 **기존 핀으로 이동할 수 있는 참조(방·핀 식별자, 최초 저장 시각)** 를 함께 담는다. (→ [[신규] 알림함](#신규-알림함))
6. 실패 처리: 단계별 실패 사유를 잡에 기록하고, 재시도 정책(횟수·백오프)과 최종 실패 시 오류 알림을 정의한다.

### [001] 튜토리얼 (온보딩)

- **프로필 설정**: 닉네임(최대 10자, "친구들이 뭐라고 부르면 좋을까요?") + **프로필 이미지**를 함께 받는다.
  - "모든 방에 사용할래요?" 체크박스는 **제거**한다. 닉네임·프로필은 최초 1회 공통 설정이다. (디자인 리뷰 확정)
  - 프로필 노출 지점이 많아(초대된 사람 표시, 장소 추가한 사람 표시) 기본 아바타 고정값보다 초기 수집이 낫다는 판단.
- **공동방 만들기**: 방 이름(최대 20자), 색상(팔레트 5색 중 선택)
  - 미리보기 성격의 UI에는 **실시간 반영/프리뷰임을 명시하는 문구**가 필요하다. 고정된 결과 화면으로 오해할 수 있다. (디자인 리뷰 확정)
- **친구 초대**: 초대 링크 공유
- **SNS 공유 연습**: "아래 공유 버튼을 눌러서 연습해보세요" — [000] 플로우를 튜토리얼 안에서 체험
- **권한 요청**: 위치·알림 권한은 스플래시 또는 초반 진입 구간에서 요청한다. (디자인 리뷰 확정 — 사용 피로를 줄이는 지연 요청안도 검토했으나 당장은 단순하게 간다)

**백엔드 관점**

- `device_id`로 유저 **생성**(create-only, → [2.1](#21-인증보안-모델-mvp)) 후 인증 토큰 발급. 닉네임·프로필 이미지를 같은 흐름에서 등록한다.
- 프로필 이미지 업로드 경로(직접 업로드 vs 사전 서명 URL)와 저장소를 정해야 한다. `users.profile_image_url`은 URL만 보관한다.
- 온보딩 시 개인방(`rooms.type = personal`, 표시명 "내 방") 자동 생성. 개인방은 고정 개념이라 나가기·삭제 대상이 아니다.
- 공동방 생성 시 `invite_code` 발급(살아있는 행 기준 유니크). 생성자가 `rooms.owner_id`가 된다.
- 알림 권한 허용 시 푸시 토큰을 등록받아야 한다. ([000] 결과 알림의 전제)
- 방 이름 입력 검증 규칙(길이·공백·특수문자 허용 범위)은 미결이다. (→ [미결 4](#7-미결-사항-open-questions))

### [002] 홈 탭 (카드 덱 탐색)

방 하나를 골라 그 방의 핀을 카드 덱으로 탐색하는 메인 화면.

- 카드는 **10개** 노출 (디자인 주석: "보여주는 카드는 10개로 합니다")
- 정렬 3종: **꾹Pick / 최신순 / 가까운순** — "카드 정렬 값 = 모든 값은 그룹 내의 순위로 정렬"
- 인터랙션: 오른쪽 스와이프 = 넘기기, 다시 왼쪽 스와이프 = 복구
- 10개 탐색 완료 시: 플로팅 버튼 클릭하면 10개 재생성, 무시하면 자연스럽게 다음 방으로 전환
- **큐레이션 상태는 개인별**이다. 카드를 넘기거나 소비해도 다른 멤버에게 영향이 가지 않는다. (디자인 리뷰 확정)
  - 표시 문구는 개인 기준으로 라벨링한다. "누가 얼마 만에 열어본 곳", "누가 추가한 곳"
- **첫 진입 튜토리얼**: 클릭하면 방을 바꿀 수 있다는 것, 카드를 좌우로 스와이프할 수 있다는 것을 안내한다. **별도 화면 단위**로 설계한다. (캐릭터 외형 미정)
- **현재 선택된 방은 고정 라벨로 노출**한다. 3초 후 사라지는 툴팁이 아니며, 방 선택 기능이 캐릭터 클릭에만 의존하지 않도록 한다. (디자인 리뷰 확정)
- **카드 내 점 3개 메뉴는 제거**한다. 이 화면은 가볍게 큐레이션을 소비하는 화면이고, 여기서 삭제/숨김 액션을 주면 공동방 개념과 충돌한다. (디자인 리뷰 확정)
- 카드 클릭 시 **장소 상세로 이동한다는 점을 명확히 표기**한다.
- 데이터 없을 때: empty state의 CTA는 "첫 장소 저장하기"가 아니라 **"방 만들기"**다. 장소를 저장하려면 방이 먼저 있어야 하기 때문. (디자인 리뷰 확정)

**백엔드 관점**

- 카드 피드는 `room_id` + 정렬 기준 + 페이지 크기(10)로 조회한다. `가까운순`은 클라이언트 좌표를 파라미터로 받는다.
- **접근 기록은 사용자별로 저장해야 한다.** 현재 `pins.last_accessed_at`은 "그룹방 내에서 누군가 마지막으로 본 시점"이라 개인별 큐레이션과 맞지 않는다. 사용자별 접근 테이블(`pin_accesses` 등) 추가가 필요하다. (→ [5장 후속 스키마](#후속-스키마-작업))
- 재생성 요청은 이미 본 카드를 제외해야 하므로, 사용자별 접근 기록을 제외 조건으로 사용한다.
- `꾹Pick` 정렬 기준은 미결이다. (→ [미결 1](#7-미결-사항-open-questions))
- 카드에 "누가 추가한 곳"을 표시하려면 `pins.created_by` 조인이 필요하다. 작성자가 탈퇴/삭제된 경우의 표시 방식(스키마상 참조는 유지됨)을 정해야 한다.

### [003] 저장탭 (방 리스트)

지도 위 바텀시트(peek / half / full 3단)로 방 리스트를 보여준다.

- 상태 구분: 개인방만 존재 / 공동방 N개 이상 존재
- 방 리스트에서 방을 선택하면 [004] 방 상세로 진입
- **바텀시트 높이는 픽셀 고정값이 아니라 화면 높이 대비 비율로 정의**한다. 기기별 높이 차이를 고려한 비율 기반 명세가 필요하다. (디자인 리뷰 확정)
- **방 생성 CTA 2개 운영 유지**: "공동방 만들기" CTA와 플러스 버튼이 함께 있는 구조를 유지한다. CTA는 초기 사용자를 위한 일회성 강조 장치이며, 방이 많아지면 사라진다. (디자인 리뷰 확정)

**백엔드 관점**

- 유저가 속한 방 목록을 반환한다. 개인방/공동방 구분, 핀 수, 방 색상·이름, 멤버 수 등 리스트 렌더링에 필요한 메타를 포함한다.
- 나간 방은 제외한다(`room_members.deleted_at`이 방을 나간 시점이므로 살아있는 멤버십만 조회).
- CTA 노출 조건(방 개수)에 쓸 수 있도록 공동방 개수를 판별 가능해야 한다.

### [004] 방 상세

방에 저장된 핀 목록과 방 단위 액션. 바텀시트 3단(peek / half / full).

- **핀 리스트**: 방의 핀들을 리스트로 확인
- **다른 방에 공유**: 핀을 다른 방으로 복제, 완료 시 토스트 피드백
  - 대상 방 목록에서 **이미 같은 장소가 저장된 방은 선택됨/비활성 상태로 표현**한다. 사용자가 해제 가능한 것처럼 보이지 않도록 처리한다. (디자인 리뷰 확정 — 서버가 판별 가능함을 개발에서 확인)
- **친구 초대**: 초대 링크 공유
- **방 편집**: 이름·색상 변경
- **방 나가기**: 모든 참여자가 가능하다.
- **방장 위임**: 방장이 나갈 때는 **위임 대상 선택 모달**을 제공한다. 자동 위임 대신 누구에게 넘어가는지 명시적으로 보여준다. (디자인 리뷰 확정)
- ~~**링크로 장소 직접 추가**~~ — 스펙 아웃 (→ [2장 비목표](#비목표-mvp에서-다루지-않음))

**권한 정책** (디자인 리뷰 확정)

| 동작 | 방장 | 일반 참여자 |
|---|---|---|
| 방 생성 | ✅ | ✅ (생성자가 그 방의 방장이 됨) |
| 방 정보 편집(이름·색상) | ✅ | ❌ |
| 방 나가기 | ✅ (위임 필요) | ✅ |
| 방장 위임 | ✅ | ❌ |
| 방 삭제 | ❌ (개념 자체를 두지 않음) | ❌ |

**백엔드 관점**

- 방 상세 = 방 정보 + 핀 리스트(지도뷰용 좌표 포함). 요청 유저의 멤버십을 검증한다.
- 방장 판별은 `rooms.owner_id`로 한다. 스키마에 이미 존재하며, 주석에도 "방장 탈퇴 시 위임은 애플리케이션에서 처리한다"고 명시되어 있다.
- 방 나가기 = `room_members.deleted_at` 기록(soft delete). 살아있는 행끼리만 유니크하므로 나갔던 방에 다시 합류할 수 있다.
- **방장이 나가는 경우 위임 대상을 함께 받아 `rooms.owner_id`를 옮긴 뒤 나가기를 처리한다.** 위임과 나가기는 한 트랜잭션으로 묶는다. 남은 멤버가 없을 때의 처리(마지막 멤버 나가기 허용 여부, 무주공산 방 처리)는 정의가 필요하다.
- 개인방(`type: personal`)은 나가기·위임·편집 대상에서 제외한다.
- 다른 방 공유 대상 목록을 줄 때 **각 방에 해당 장소가 이미 저장되어 있는지**를 함께 반환한다. `pins`를 `place_id`로 조회해 판별 가능하다.
- 핀 복제 시 원본 방·대상 방 **양쪽 멤버십**을 검증한다.

### [005] 지도뷰 & 장소 상세

- **지도뷰**: 방의 핀들을 지도 위에 표시
- **카테고리 버튼(카페·음식점 등)은 바텀시트 내부가 아니라 지도 상단에 배치**한다. (디자인 리뷰 확정 — 바텀시트가 담는 정보가 과했음)
- **장소 상세**: 장소 정보(이름·주소·카테고리 등) + 출처 링크 + 코멘트 (half / full)
- **코멘트**: 방 멤버가 핀에 코멘트 작성 (empty state: "아직 코멘트가 없어요!")
- **다른 방에 공유 / 새 방 만들기**: 장소 상세에서 바로 다른 방으로 공유하거나, 새 공동방을 만들어 공유
- **외부 지도 앱 이동 버튼**: 기존 라이팅이 실제 경로 탐색 기능처럼 오해될 수 있어 **라이팅 수정이 우선**이다. 카카오맵만 가능한 제약이 있어 아이콘 중심 표현은 애매하고, 복잡한 선택 모달은 현 단계에서 과하다. (디자인 리뷰 확정)
- **바텀시트 X 버튼은 전반적으로 제거**하되, **장소 상세의 풀페이지 상태는 예외**로 종료/뒤로가기 동작이 필요하다. 안드로이드 물리 뒤로가기와 동일 동작으로 정의해야 하며, 구체 정책은 미결이다. (→ [미결 3](#7-미결-사항-open-questions))

**백엔드 관점**

- 지도뷰는 [004] 방 상세의 핀 리스트를 좌표와 함께 재사용한다. 별도 엔드포인트를 두지 않는다.
- 카테고리 필터는 `places`의 카테고리 값 기준이다. 지오코더(Kakao/Google) 응답의 카테고리 체계가 provider마다 달라 **표시용 카테고리 정규화 규칙**이 필요하다.
- 장소 상세 = 장소 정보 + 출처 링크(`place_sources` → `sources.original_url`) + 코멘트 목록/수.
- 코멘트 작성·조회·삭제 모두 방 멤버십을 검증한다. 삭제는 soft delete(`pin_comments.deleted_at`)로 처리한다. **수정은 MVP 미지원**(삭제 후 재작성)이며 수정 API를 두지 않는다.
- 외부 지도 앱 이동은 클라이언트가 좌표·장소명으로 딥링크를 구성한다. 서버 작업 없음.

### [006] 친구 초대

- 초대 링크(`ssokpin.org/r/{code}`) 생성·공유
- 링크로 진입한 사용자는 프로필 설정 후 해당 방의 멤버가 된다 (Case 2 온보딩)
- 중복 참여는 불가 (`room_members (room_id, user_id)` 살아있는 행 유니크)

**백엔드 관점**

- 초대 코드로 방을 미리보기하는 조회는 **인증 없이** 가능해야 한다(앱 설치 전/온보딩 전 진입). 노출 범위는 방 이름·색상·멤버 수 정도로 최소화한다.
- 합류는 인증 후 처리하며, 이미 멤버면 오류 대신 멱등 응답을 준다.
- 나갔던 방에 같은 초대 코드로 재합류하면 새 `room_members` 행이 생긴다(이전 행은 `deleted_at` 유지).
- 초대 코드는 `rooms.invite_code`(최대 16자)에 보관되며 방당 1개다. 코드 재발급·만료 정책은 MVP에 없다.

### [신규] 마이페이지

다음 기능을 담기 위해 마이페이지가 필요하다는 것이 회의 결론이다. (디자인 리뷰 확정)

- **약관 노출**
- **테마 변경**
- **닉네임/프로필 수정**

**백엔드 관점**

- 닉네임·프로필 이미지 수정은 [001]에서 만든 프로필 API를 재사용한다. 공통 프로필이므로 모든 방에 즉시 반영된다.
- 테마는 클라이언트 로컬 설정으로 두면 서버 작업이 없다. 기기 간 동기화가 필요하면 사용자 설정 저장이 추가된다 — **범위 정의 필요**. (기획 액션 아이템)
- 약관은 정적 문서 링크로 처리한다. 버전 관리·동의 이력이 필요하면 별도 설계가 필요하다.
- 계정 탈퇴는 MVP 비목표다. (스키마에는 `users.deleted_at`과 활성 행 부분 유니크가 이미 있어 나중에 붙일 수 있다)

### [신규] 알림함

[000]의 처리 결과를 사용자가 다시 확인할 수 있는 화면. 오류성 이벤트 전용 페이지보다 **알림함 UI**가 자연스럽다는 결론이다. (디자인 리뷰 확정)

- 성공 / **중복 저장** / 오류 알림을 시간순으로 모아 본다.
- **중복 저장 알림은 "이미 저장되어 있습니다"만으로 부족하다.** 언제 저장했는지, 어느 방에 있는지를 알 수 있어야 하고, 가능하면 **기존 저장 위치로 바로 이동**할 수 있어야 한다.
- 푸시 알림을 탭했을 때의 도착 지점도 같은 원칙을 따른다.

**백엔드 관점**

- 알림 레코드 테이블이 필요하다: 수신자, 유형(성공/중복/오류), 참조 대상(방·핀·분석 잡), 생성 시각, 읽음 시각.
- 중복 알림은 **기존 핀의 방·핀 식별자와 최초 저장 시각**을 함께 담아야 "어디에 언제" 질문에 답할 수 있다.
- 푸시 발송을 위해 사용자별 디바이스 푸시 토큰 저장이 필요하다(FCM/APNs). 토큰 갱신·만료 처리 포함.
- 알림 목록 조회는 페이지네이션, 읽음 처리는 개별/일괄 모두 필요할 수 있다.

## 5. 데이터 모델 개요

PR #44에서 8개 테이블이 정의·머지됐다. **모든 테이블에 soft delete(`deleted_at`)가 적용**되어 있고, 유니크 제약은 살아있는 행에만 걸리는 **부분 유니크 인덱스**로 구현되어 있다(삭제 후 재생성 가능).

| 테이블 | 역할 | 비고 |
|---|---|---|
| `users` | device_id 기반 사용자 | 닉네임(10자)·프로필 이미지. `device_id`는 살아있는 행끼리만 유니크 |
| `rooms` | 방 | `type`: `personal` / `shared`, **`owner_id`(방장)**, 이름(20자)·색상(hex 7자)·`invite_code`(16자, 활성 유니크) |
| `room_members` | 방 멤버십 | `(room_id, user_id)` 활성 유니크. `deleted_at` = **방을 나간 시점** |
| `sources` | 출처 링크 | `type`: instagram / naver_map / google_map / manual, `original_url` 활성 유니크, `metadata`(스크랩 원문 jsonb) |
| `places` | 장소 마스터 | `(provider, provider_place_id)` 유니크로 dedup (provider: kakao / google) |
| `place_sources` | 장소↔출처 N:M | `(place_id, source_id)` 활성 유니크로 재유입 시 기존 연결 재사용 |
| `pins` | 방에 저장된 장소 | `(room_id, place_id)` 활성 유니크, `source_id`·`created_by` nullable, `last_accessed_at` |
| `pin_comments` | 핀 코멘트 | 작성자가 방 멤버인지는 애플리케이션 레벨에서 검증 |

### 후속 스키마 작업

회의 결정으로 다음 스키마 추가가 필요하다. 각각 별도 태스크로 다룬다.

| 대상 | 사유 | 근거 |

## 7. 미결 사항 (Open Questions)

확정되지 않아 관련 피쳐 개발 전 결정이 필요한 항목.

1. **꾹Pick 정렬 기준**: 디자인 주석에 "중복 저장 데이터로 정렬"과 "코멘트수로 정렬"이 혼재되어 있다. 어느 기준인지(혹은 복합 기준인지) 확정 필요. 데이터로는 `place_sources` 수(중복 저장) / `pin_comments` 수(코멘트) 모두 산출 가능하다.
2. **초대 수락과 닉네임 설정 순서**: 초대 맥락을 먼저 보여주는 안과, 공통 프로필 1회 설정이므로 진입 시 먼저 받는 안이 갈렸다. 전체 사용자 플로우 정리본이 나온 뒤 판단한다.
3. **장소 상세 풀페이지의 X/뒤로가기 정책**: 바텀시트 X 버튼은 전반적으로 제거하되 풀페이지는 예외다. 네이버 지도 유사 패턴 차용 여부, 안드로이드 물리 뒤로가기와의 동작 일치를 문서화해야 한다.
4. **방 이름 입력 정책**: 길이·공백 외에 **특수문자 허용 여부**와 입력 제한 규칙, 정규식 명세가 필요하다.
5. **"다른 방에 공유" UI 형태**: 바텀시트가 최선인지 검토 여지가 있다. 뒤에 맥락 화면이 있으면 바텀시트가 적절하지만, 독립적 선택이 필요한 경우 모달/페이지가 나을 수 있다.
6. **마이페이지 범위**: 약관·테마·프로필 수정 외에 무엇을 담을지, 테마 설정을 서버에 저장할지.
7. **방장이 마지막 멤버일 때의 나가기 처리**: 위임 대상이 없으면 나가기를 막을지, 방을 비활성 처리할지. (방 삭제는 비목표)
8. **초대 링크 수명주기 정책**: 현재는 방 생성 시 발급한 코드가 만료 없이 계속 유효하다(링크 = 접근 권한, → [2.1](#21-인증보안-모델-mvp)). 코드 만료·폐기/재발급, 방 최대 인원 제한, 초대 미리보기 노출 정보 범위는 오남용 사례를 보고 도입 여부를 판단한다.

## 8. API 설계 초안 (RESTful Draft)

경로·메서드 수준의 초안이다. 요청/응답 스키마, 에러 코드, 페이지네이션 상세는 각 피쳐 PR에서 확정한다.

**공통 규칙**

- 베이스 경로: `/api/v1` (기존 `PlaceController` 컨벤션 유지)
- 인증: `Authorization: Bearer <token>` — **인증 예외는 `POST /users`와 `GET /invitations/{code}` 둘뿐이다.**
- 리소스는 복수형 명사, 동작은 HTTP 메서드로 표현한다. 상태 변경 기록처럼 명사화가 자연스러운 동작은 하위 컬렉션(`/accesses`)으로 표현한다.
- 부분 수정은 `PATCH`, 컬렉션 추가는 `POST`
- 방 스코프 리소스는 전부 요청 유저의 멤버십을 검증한다.

### 유저 · 마이페이지

| Method | Path | 설명 | 화면 |
|---|---|---|---|
| `POST` | `/api/v1/users` | **유저 등록 (create-only)** + 인증 토큰 발급. 이미 등록된 `device_id`면 `409` | [001] |
| `GET` | `/api/v1/users/me` | 내 프로필 조회 | [001] [마이페이지] |
| `PATCH` | `/api/v1/users/me` | 프로필 수정 (닉네임 10자 / 프로필 이미지) | [001] [마이페이지] |
| `PUT` | `/api/v1/users/me/push-token` | 디바이스 푸시 토큰 등록·갱신 | [알림함] |

> `POST /users`를 upsert로 두면 인증 예외 엔드포인트에서 타인의 `device_id`로 토큰을 받아갈 수 있다. create-only가 이 설계의 전제다. (→ [2.1](#21-인증보안-모델-mvp))

### 방 (Room)

| Method | Path | 설명 | 화면 |
|---|---|---|---|
| `POST` | `/api/v1/rooms` | 공동방 생성 (이름 20자·색상, `invite_code` 발급, 생성자가 `owner_id`) | [001] [005] |
| `GET` | `/api/v1/rooms` | 내가 속한 방 목록 (개인방/공동방 구분, 핀 수 등 메타 포함) | [003] |
| `GET` | `/api/v1/rooms/{roomId}` | 방 상세 (방 정보 + 핀 리스트, 지도뷰용 좌표 포함) | [004] [005] |
| `PATCH` | `/api/v1/rooms/{roomId}` | 방 편집 (이름·색상) — **방장만** | [004] |
| `PUT` | `/api/v1/rooms/{roomId}/owner` | 방장 위임 (body: `nextOwnerId`) — **방장만** | [004] |
| `DELETE` | `/api/v1/rooms/{roomId}/members/me` | 방 나가기. 방장이면 body에 `nextOwnerId` 필수 | [004] |

**세부 계약 메모**

- `GET /rooms`: `?savedPlaceId={placeId}`를 주면 각 방에 해당 장소가 이미 저장되어 있는지를 함께 반환한다. "다른 방에 공유" 화면에서 이미 저장된 방을 선택됨/비활성으로 그리는 데 쓴다.
- `DELETE /rooms/{roomId}/members/me`: 방장의 나가기는 위임과 한 트랜잭션으로 처리한다. 위임 대상 없이 요청하면 거절한다. 개인방은 나가기 대상이 아니다.
- 방 **삭제 엔드포인트는 두지 않는다.** (비목표)

### 초대 / 멤버십

| Method | Path | 설명 | 화면 |
|---|---|---|---|
| `GET` | `/api/v1/invitations/{code}` | 초대 코드로 방 미리보기 (**인증 불필요**, 노출 정보 최소화) | [006] |
| `POST` | `/api/v1/rooms/{roomId}/members` | 방 합류 (body에 `inviteCode`). 이미 멤버면 멱등 처리 | [006] |
| `GET` | `/api/v1/rooms/{roomId}/members` | 방 멤버 목록 (방장 위임 대상 선택 모달용) | [004] |

> `POST /rooms/{roomId}/members`는 "멤버 컬렉션에 나를 추가"로 읽힌다. `/join` 같은 동사 경로를 쓰지 않는 이유이며, 나가기(`DELETE .../members/me`)와도 대칭을 이룬다.

**세부 계약 메모**

- `POST /rooms/{roomId}/members`: body의 `inviteCode`가 **path의 `{roomId}`에 속한 활성 코드인지 검증**하고, 불일치하거나 무효한 코드는 멤버 추가 전에 거절한다. path와 코드의 대상이 다르면 잘못된 방에 가입시키는 구현이 가능하기 때문이다.

### 링크 분석 (비동기) · 핀

| Method | Path | 설명 | 화면 |
|---|---|---|---|
| `POST` | `/api/v1/link-analyses` | **링크 분석 요청 → `202 Accepted` + `jobId`** (즉시 응답) | [000] |
| `GET` | `/api/v1/link-analyses/{jobId}` | 분석 잡 상태 조회 (대기/처리중/성공/중복/실패) | [000] |
| `POST` | `/internal/link-analyses/{jobId}/process` | **Cloud Tasks 워커 콜백** (OIDC 가드, 외부 비공개) | — |
| `GET` | `/api/v1/rooms/{roomId}/cards` | 홈 카드 피드 조회 (10개) | [002] |
| `GET` | `/api/v1/pins/{pinId}` | 장소(핀) 상세 — 장소 정보 + 출처 링크 + 코멘트 수 | [005] |
| `POST` | `/api/v1/rooms/{roomId}/pins` | 다른 방에서 핀 복제 (body: `{ "pinId": ... }`) | [004] [005] |
| `POST` | `/api/v1/pins/{pinId}/accesses` | 핀 접근 기록 (**사용자별**) | [002] |

**세부 계약 메모**

- `POST /link-analyses`: body는 `{ url, roomId }`. **잡 생성 전에 `roomId`에 대한 요청 유저의 멤버십을 검증한다.** 서버는 `sources` 등록과 잡 생성까지만 동기로 하고 즉시 `202`를 반환한다. 스크랩·LLM·지오코딩 지연 때문에 동기 응답이 불가하다는 것이 회의 결론이다.
  - 기존 `POST /api/v1/place/places`(`src/modules/place/place.controller.ts`)가 동기 추출을 하고 있어, 이 경로로 정리하며 흡수한다.
  - MVP 지원 출처는 인스타그램 링크뿐이다. 그 외 URL은 명시적으로 거절한다.
- `GET /link-analyses/{jobId}`: 푸시가 주 전달 수단이지만, 앱이 포그라운드일 때 폴링/보정용으로 필요하다. **잡 생성 요청자(또는 해당 방 멤버)만 조회할 수 있다** — 잡 상태·실패 사유가 무관한 사용자에게 노출되면 안 된다.
- `POST /rooms/{roomId}/pins`: **신규 저장 경로는 이 엔드포인트에 없다.** 신규 저장은 링크 분석 잡이 백그라운드에서 처리하므로, 이 엔드포인트는 "다른 방에 공유(복제)" 전용이다. 원본 방·대상 방 양쪽 멤버십을 검증한다.
  - 대상 방에 같은 장소가 이미 있으면 신규 생성 대신 기존 핀을 반환한다. 정확한 상태 코드(200 vs 409)는 구현 PR에서 확정.
- `GET /rooms/{roomId}/cards`: `?sort=pick|recent|nearby`, `nearby`는 `lat`/`lng` 필수. 10개 재생성은 **사용자별 접근 기록**을 제외 조건으로 사용한다. `pick` 정렬 기준은 미결 1.
- `POST /pins/{pinId}/accesses`: 개인별 큐레이션이 확정됐으므로 요청 유저 기준으로 접근 행을 남긴다. `pins.last_accessed_at` 갱신만으로는 부족하다.

| `GET` | `/api/v1/pins/{pinId}/comments` | 코멘트 목록 조회 | [005] |

  - 큐 enqueue 서비스 + 워커 엔드포인트 OIDC 인증 가드. 큐 리소스는 `infra/`에 이미 정의되어 있고, 앱 연동만 미머지 상태다.
- **링크 유입 > DB > 링크 분석 잡 테이블**
  - 상태(대기/처리중/성공/중복/실패), 실패 사유, 재시도 횟수, 요청 유저·대상 방 참조.
- **링크 유입 > API > 링크 분석 접수 (비동기)** — `POST /link-analyses`, `GET /link-analyses/{jobId}`
  - `original_url` 정규화 → `sources` 조회·등록 → 잡 생성 → **즉시 202**. 인스타그램 URL만 허용.
  - 기존 `POST /api/v1/place/places`를 이 경로로 정리·흡수.
- **링크 유입 > Worker > 장소 추출 파이프라인 처리** — `POST /internal/link-analyses/{jobId}/process`
  - 스크래핑 → AI 추출 → 지오코딩 → `places` dedup → `place_sources` 연결 → `pins` 생성.
  - 같은 방 중복(`(room_id, place_id)` 활성 유니크) 시 중복 결과로 종결. 단계별 실패 기록 + 재시도 정책.

### [신규] 알림함 · 푸시

- **INFRA > Push > FCM/APNs 발송 연동**
  - 발송 클라이언트 + 자격증명 관리. 신규 인프라 작업.
- **알림 > DB > 알림 · 디바이스 푸시 토큰 테이블**
  - 수신자·유형·참조 대상(방/핀/잡)·읽음 시각. 중복 알림은 기존 핀 참조와 최초 저장 시각 포함.
- **알림 > API > 푸시 토큰 등록 / 알림 목록·읽음 처리** — `PUT /users/me/push-token`, `GET /notifications`, `POST /notifications/reads`
  - 분석 잡 종결 시 알림 생성 + 푸시 발송 훅 연결.

### [001] 튜토리얼 · [006] 친구 초대

- **방 > API > 방 생성** — `POST /rooms`
  - 공동방 생성(이름 20자·색상·`invite_code` 발급, 생성자가 `owner_id`). 온보딩 시 개인방(`type: personal`) 자동 생성 규칙 포함.
  - 방 이름 입력 검증(길이·공백·특수문자)은 미결 4 확정 후 반영.
- **방 > API > 초대 코드로 방 참여** — `GET /invitations/{code}`, `POST /rooms/{roomId}/members`
  - 초대 코드로 방 미리보기(인증 불필요, 노출 정보 최소화) + `room_members` 합류. 중복 참여 시 멱등 처리.

### [002] 홈 탭

- **핀 > DB+API > 사용자별 핀 접근 기록** — `POST /pins/{pinId}/accesses`
  - 개인별 큐레이션 확정에 따른 사용자별 접근 테이블 추가 + 기록 API.
- **홈 > API > 카드 피드 조회** — `GET /rooms/{roomId}/cards`
  - 방별 핀 카드 10개 조회. 정렬 3종: 꾹Pick(기준 미결 1) / 최신순 / 가까운순(좌표 파라미터).
  - 재생성 시 **사용자별 접근 기록으로 이미 본 카드 제외**. "누가 추가한 곳" 표시용 `created_by` 조인 포함.

### [003] 저장탭

- **방 > API > 방 리스트 조회** — `GET /rooms`
  - 유저가 속한 방 목록(개인방/공동방 구분, 핀 수 등 메타 포함, 나간 방 제외).
  - `?savedPlaceId=`로 "다른 방에 공유" 화면의 이미 저장된 방 판별 지원.

### [004] 방 상세 · 권한

- **방 > API > 방 상세 조회** — `GET /rooms/{roomId}`
  - 방 정보 + 핀 리스트(지도뷰용 좌표 포함). 멤버십 검증.
- **방 > API > 방 편집** — `PATCH /rooms/{roomId}`
  - 이름·색상 수정. **방장 권한 검증**.
- **방 > API > 방 나가기 · 방장 위임** — `DELETE /rooms/{roomId}/members/me`, `PUT /rooms/{roomId}/owner`, `GET /rooms/{roomId}/members`
  - 방장 나가기 시 위임 대상 필수, 위임+나가기 한 트랜잭션. 개인방 제외. 마지막 멤버 처리는 미결 7.
- **핀 > API > 다른 방에 공유 (핀 복제)** — `POST /rooms/{roomId}/pins`
  - 원본 방·대상 방 **양쪽 멤버십 검증**. 대상 방에 같은 장소가 있는 경우 응답 정책 포함.

### [005] 지도뷰 & 장소 상세

- **핀 > API > 장소(핀) 상세 조회** — `GET /pins/{pinId}`
  - 장소 정보(이름·주소·카테고리 등) + 출처 링크 + 코멘트 목록/수.
  - 지도 상단 카테고리 필터를 위한 **provider별 카테고리 정규화 규칙** 정의 포함.
- **코멘트 > API > 핀 코멘트 작성·조회·삭제** — `GET·POST /pins/{pinId}/comments`, `DELETE /pins/{pinId}/comments/{commentId}`
  - 방 멤버 검증. 삭제는 soft delete.

### [신규] 마이페이지

- **유저 > API > 마이페이지 설정** — 범위 확정 후 착수 (미결 6)
  - 프로필 수정은 공통 유저 API 재사용. 테마를 서버에 저장할지 결정 필요. 약관은 정적 링크.
